# PPL 训练摘要：渐进式详情产品 Demo 方案

> 状态：初步产品方案  
> 目的：当第一人称识别无法稳定到具体动作时，仍让用户获得可信、低负担的训练总结；把“要看多细”交还给用户。

## 1. 一句话定义

用户结束训练后，首页先告诉他“今天做了多少组推、拉、腿、直接核心”，并用一张**估算的肌群覆盖图**呈现训练结构；只有用户想深挖或系统存在不确定项时，才进入具体动作确认。用户修正动作后，外层的组数和肌群图同步变为更精确的结果。

它不是把具体动作识别藏起来，而是把它放到用户真正需要它的时候。

---

## 2. 为什么要这样设计

第一人称视频对“具体动作”并非始终可靠：同一个龙门架、相近的手臂轨迹，可能对应高位下拉、坐姿划船或绳索下压。但系统通常仍能更稳定地判断它是推、拉还是腿部训练。

如果首页直接列出十几条具体动作，用户会遇到两个问题：

- 识别错一个动作，整份报告看起来就不可信；
- 即使识别正确，用户也会被动作名、次数、肌群、置信度等细节淹没。

而“推 8 组、拉 6 组、腿 4 组”已经足以回答大多数训练后的问题：今天练了什么？训练是否偏科？本周是否漏了腿？下一次该练什么？

具体动作仍然重要，但它应该服务于两类用户：想复盘训练的人，以及愿意用一次确认换取更精确追踪的人。

---

## 3. 产品原则

1. **先给答案，再给证据。** 首页优先展示训练结构，不把用户推到明细表里。
2. **不确定时降级，不硬猜。** 识别不够确定时，显示推 / 拉 / 腿，而不是编造一个具体动作。
3. **详情按需展开。** 用户主动点击“查看与确认动作”，才看到每一组的具体识别结果。
4. **一次修正，多处更新。** 修正具体动作后，动作列表、PPL 组数、肌群图、周训练统计和计划完成度都由同一份数据回算。
5. **估算与确认必须可区分。** 不能把“按推类规则估算胸肩三头覆盖”说成用户已经精确训练了这些肌肉。

---

## 4. 分类与肌群映射规则（产品语言）

### 4.1 用户看到的训练结构

首屏使用五类：

| 类别 | 定义 | 首屏是否计组 |
| --- | --- | --- |
| 推 | 以胸、前三角、三头发力为主的推举、推胸、夹胸、下压等 | 是 |
| 拉 | 以背、后束、二头为主的下拉、划船、引体、弯举等 | 是 |
| 腿 | 深蹲、髋铰链、腿举、腿屈伸、提踵等下肢训练 | 是 |
| 直接核心 | 卷腹、平板、举腿、腹轮等以核心为主要目标的训练 | 是，单列 |
| 有氧 / 其他 | 跑步、单车、热身、拉伸、无法归类动作 | 不并入 PPL 组数，单独展示时长 |

这里的“核心”是**直接核心训练**。推、拉、腿训练会调用核心稳定，但不应因为做了卧推就虚增一组核心训练。

### 4.2 首页肌群图的两种状态

| 数据状态 | 肌群图如何计算 | 对用户怎么说 |
| --- | --- | --- |
| PPL 估算 | 根据推 / 拉 / 腿的已识别组数，按默认权重分配到相关肌群 | “按训练类型估算” |
| 动作已确认 | 根据用户确认后的具体动作及其主/辅肌群映射计算 | “已按动作确认” |

建议默认权重仅用于视觉概览，不用于医疗、康复或精细训练处方：

| 大类 | 首页默认展示的主要覆盖 | 说明 |
| --- | --- | --- |
| 推 | 胸、肩、三头 | 三者展示为同等级或接近同等级的“覆盖”，避免伪造精确刺激比例 |
| 拉 | 背、后肩、二头 | 默认强调背；后肩和二头作为共同覆盖 |
| 腿 | 股四头、臀、腘绳肌、小腿 | 默认显示为下肢整体覆盖，不把深蹲与硬拉混成相同的精确比例 |
| 直接核心 | 腹部、侧腹、下背稳定 | 仅由直接核心组触发明显覆盖 |

**重要表达规则：** 首屏图例写“覆盖估算”，而非“肌肉训练量”；一旦用户确认动作，图例才改为“基于已确认动作”。

## 5. Demo 场景：一次训练从结束到确认

### 场景 A：大多数用户，只看首屏

用户完成 45 分钟训练。系统从视频识别出：推类 8 组、拉类 4 组、腿部 3 组；其中两段具体动作不够确定。

首屏文案：

```text
今天的训练

15 组力量训练 · 45 分钟

推  8 组        拉  4 组        腿  3 组
████████        ████            ███

直接核心 0 组 · 有氧 8 分钟

本次以推为主，胸、肩、三头覆盖较多；
本周腿部训练仍偏少。

[查看训练详情与确认动作]
```

用户不点详情，产品已经完成了最重要的价值：记录了训练、展示了结构、给出了可理解的平衡提示。

### 场景 B：用户想知道“这几组到底是什么”

用户点击“查看训练详情与确认动作”，进入按大类折叠的明细页：

```text
训练详情                                              已确认 9 / 15 组

推 · 8 组
  ✓ 固定器械推胸                3 组
  ? 推类器械训练                3 组   [确认]
  ✓ 绳索下压                    2 组

拉 · 4 组
  ? 拉类器械训练                2 组   [确认]
  ✓ 高位下拉                    2 组

腿 · 3 组
  ✓ 腿举                         3 组
```

“?” 不显示一串模型术语，而是只在用户点击后给候选：

```text
这 3 组推类训练更像哪一种？

[固定器械推胸]  [蝴蝶机夹胸]  [推肩]  [不是以上动作]

系统依据：识别到坐姿器械与向前推的动作轨迹。
```

用户只需确认他在意的段。未确认的段继续作为“推类训练”服务于 PPL 摘要，不被强行删除。

### 场景 C：用户修正后，外层同步变化

用户将“推类器械训练 3 组”从“固定器械推胸”改成“推肩”。系统不只是替换一行文字，而是立即回算：

```text
修正前：推 8 组；覆盖估算 = 胸 / 肩 / 三头
修正后：推 8 组不变；已确认动作覆盖 = 胸 3 组、肩 3 组、三头 2 组
```

首页的训练结构不需要变化，因为仍属于推；但肌群图从“推类估算”变成更精确的胸、肩、三头覆盖。周统计与计划完成情况也读取同一份修正后的动作数据。

## 6. 前端信息架构

### 6.1 训练完成页 / 首页卡片

优先级从上到下：

1. 本次训练总时长、力量组数；
2. 推 / 拉 / 腿三列组数；
3. 直接核心与有氧时长；
4. 简化肌群覆盖图；
5. 一句训练结构提示；
6. “查看详情与确认动作”入口。

肌群图不应比 PPL 组数更抢眼。它是帮助用户理解结构的可视化，不是让用户逐块审查人体模型的入口。

### 6.2 详情与确认页

详情页仍然优先按推 / 拉 / 腿分组，而不是把动作按时间平铺。用户需要时可以切换到“时间线”看训练过程。

每一个训练段显示：

- 当前层级：已确认具体动作 / 系统推荐动作 / 仅大类；
- 组数；
- 置信提示：只把低置信且影响结果的段标成“待确认”；
- 编辑入口；
- 可选的证据回看，例如短视频片段或关键帧。

不要显示裸露的 `0.73 confidence`。对用户而言，“系统已确认”“建议确认”“仅识别到拉类”更有意义。

### 6.3 周视图

周视图默认回答的是训练分化与覆盖，而不是逐动作排行榜：

```text
本周训练结构

推 16 组     拉 12 组     腿 6 组     直接核心 2 组

你的训练以推为主；腿部组数低于你过去四周的平均水平。
[查看具体动作与已确认训练]
```

当具体动作被确认得更多，周视图可自然细化为“高位下拉 6 组、坐姿划船 4 组”；但不要求所有用户先完成确认，才能得到周结构。

## 7. 数据与回算逻辑

### 7.1 每个训练段至少需要保存的字段

```json
{
  "segment_id": "seg_018",
  "sets": 3,
  "coarse_category": "push",
  "coarse_confidence": "high",
  "exercise_id": "machine_chest_press",
  "exercise_confidence": "low",
  "resolution": "coarse_only | system_suggested | user_confirmed",
  "user_corrected_exercise_id": null
}
```

关键点：`coarse_category` 是独立字段，不是从最终动作名临时反推。这样具体动作未知或被用户留空时，推 / 拉 / 腿组数仍可稳定存在。

### 7.2 回算优先级

```text
用户确认的具体动作
  > 系统高置信的具体动作
  > 系统识别的大类（推 / 拉 / 腿 / 直接核心）
  > 未分类训练片段
```

肌群图的计算顺序：

```text
已确认具体动作 → 用动作的主/辅肌群映射
未确认但有 PPL → 用 PPL 的默认覆盖规则，并标记为估算
未分类 → 不进入肌群图，只保留在训练时长中
```

### 7.3 什么会触发用户确认

不应因为每一个低置信动作都打扰用户。建议仅在下列情况出现确认卡：

- 某段在两个具体动作之间摇摆，且会显著改变肌群图；
- 系统识别与用户计划冲突；
- 同一段候选跨越两个大类，例如推与拉无法确定；
- 用户主动进入详情，想补全数据。

如果候选都属于拉，例如高位下拉与坐姿划船，首页不必打断用户；详情页再提供确认即可。

## 8. 与现有 fitness-v1 资产的关系

现有动作映射已经包含不少 `push`、`pull`、`squat`、`hinge`、`extension` 等动作模式，也有肌群映射和周肌群统计。因此本 Demo 不是另建一套动作知识库。

需要补的是产品层的统一规则：

```text
push                         → 推
pull / curl                  → 拉
squat / hinge / extension   → 腿
直接核心动作                 → 直接核心
cardio                       → 有氧
raise / 其他                 → 依据动作映射；无法确定则其他
```

其中 `curl` 和 `raise` 不宜机械归类：弯举通常可以进入拉；侧平举则应由动作映射决定是否算推日肩部训练，或单独标成肩部辅助训练。这个边界需要由运动科学规则表固定，不应临时交给模型自由判断。

## 9. MVP 验收标准

该 Demo 第一阶段不以“具体动作 top-1 准确率”作为唯一成功标准，而应同时验证：

| 指标 | 要回答的问题 |
| --- | --- |
| PPL 大类准确率 | 推 / 拉 / 腿能否明显比具体动作更可靠？ |
| 组数误差 | 用户看到的推拉腿组数是否可信？ |
| 首屏完成率 | 不进详情的用户是否仍认为总结有用？ |
| 平均确认次数 | 用户每次训练需要花多少次点击才能校正关键结果？ |
| 确认后肌群图变化率 | 系统的“覆盖估算”与具体动作真值差距有多大？ |
| 周留存/复盘率 | 这种低摩擦摘要是否让用户更愿意看训练历史？ |

建议先用 20-30 段真实训练做静态 Demo：同一批训练分别展示“直接给动作明细”和“先给 PPL 摘要，再按需确认”，观察用户是否更快理解自己的训练结构、是否更愿意完成关键确认。

---

## 10. 需要避免的误导

- 不把 PPL 估算称为精确肌肉训练量。
- 不因推、拉、腿训练存在稳定需求，就把核心组数自动加进去。
- 不因用户未确认具体动作，就让整段训练从报告里消失。
- 不把“确认动作”设计成填写表单；它必须是少量、可跳过、带候选的轻交互。
- 不让用户修正后只有详情页变化。首页、肌群图、周统计、计划完成度必须同步更新，否则确认没有回报感。

## 结论

这个方案将识别精度的不足转成一种更好的产品节奏：系统先完成用户最在意的训练结构总结，再邀请少数有意愿的用户共同把记录变精确。

用户不必一进入产品就面对大量动作细节；但当他真的在意“我今天练的到底是推胸还是推肩”时，系统也能给他控制权，并让这一次修正立刻改善整份训练记录。
