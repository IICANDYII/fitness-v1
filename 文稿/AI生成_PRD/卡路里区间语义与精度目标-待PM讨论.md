# 卡路里区间的语义:报"条件不确定度",不报"跨条件波动"(待与 PM 讨论)

> **结论(待 PM 拍板)**:用户看到的卡路里区间,应只反映**"给定这张照片/这次拍摄条件下"的不确定度(条件不确定度)**;**不应**把"换个光照/换个模型,结果会变"的**跨条件波动**塞进区间。
> - 前者让 `800–900` 这样的区间有意义、可用;
> - 后者会把同一餐撑成 `500–1200`,对用户没有意义——用户不想看到"结果随光照漂移"。
>
> 跨条件波动是另一个东西:它是一个**单独要度量、并想办法压低的鲁棒性指标**,不是区间宽度。
>
> **当前优先级**:先回答"卡路里识别 + 营养结构分析这个下游任务,在给定条件下到底能做到多准",而不是先把区间做得"全面诚实"。

## 0. 已确认(与 PM,2026-06-09)

1. **用户侧只展示一个具体点值** —— 区间会让用户困惑,不给用户看区间。
2. **内部评测保留完整区间** —— 评测要同时看点值的准度 + 区间的覆盖率。

**对设计的约束(后续一律按此)**:
- 单餐输出**两路并存**:`display_kcal`(点值,用户侧)+ `kcal_range`(区间,仅评测 / 内部 viewer)。
- 点值 = 各菜「最可能值」之和;建议 `DishEnergy` 让 LLM **直接给 per-dish 最可能点 `kcal`**(连同 low/high),避免"不对称区间取中点"带来的偏差。
- 内部区间 = 各菜独立误差**平方和开根**合成(条件不确定度,见 §2/§3),只进评测、不进用户界面。
- 评测**主指标 = 点值的 per-meal MAPE**;次指标 = 内部区间覆盖率。
- §2/§3 "条件 vs 跨条件"的原则不变,只是落点从"给用户看的区间"改成"内部评测的区间";**用户侧的诚实性改由 Pending / 置信表达**(数据不足、分歧大 → 转待确认),而不是甩给用户一个宽区间。

## 1. 问题

把"模型/光照"等外界因素的偏差也算进区间,理论上更"诚实",但实践上会出现:
- 原本(给定条件下):`800–900`
- 加上跨条件偏差后:`500–1200`

第二种对用户**无意义**:它既不能指导行动,又把"这道菜本身难估"和"外界条件在变"两件事混在一起,还摧毁了"卡路里识别"这个功能的产品价值。

## 2. 两种不确定度,必须分开(全方差公式)

`Var(估计) = E[Var(估计 | 条件)]  +  Var(E[估计 | 条件])`

| | 含义 | 该怎么处理 |
|---|---|---|
| **条件不确定度** `E[Var(估计\|条件)]` | 给定同一张照片/场景/光照,估计本身有多不准 | **→ 这才是用户区间该反映的**(窄、可用) |
| **跨条件波动** `Var(E[估计\|条件])` | 换光照/换模型/换角度时,期望估计会漂多少 | **→ 单独的鲁棒性指标**,目标是压低它,**不进用户区间** |

我们之前讨论的"给模型/光照偏差留个相关系数 ρ 把区间撑宽"——本质就是把第二项注进了用户区间,**应当撤掉**。

## 3. 决策方向(待 PM 确认)

1. **用户区间 = 条件不确定度**:由各道菜在给定条件下的独立误差合成(平方和开根,见 [营养层-Agentic-RAG-设计.md](营养层-Agentic-RAG-设计.md) 的区间合并),**不注入跨条件偏差**。
2. **跨条件稳定性 = 单独鲁棒性指标**:同一餐换光照/换模型/换角度,看估计漂多少;目标是用更好的模型/提示词/多帧把它压低,而**不是显示给用户**。
3. **理想形态**:跨条件波动 → 0(条件再变,结论稳),且**在给定条件下给出一个可靠估计**。

## 4. 这对评测的含义(近期主线)

- **主指标(固定条件下测)**:per-meal MAPE、营养结构(P/F/C 供能占比)准确率、区间覆盖率。
- **鲁棒性指标(单独测)**:同餐不同条件下的估计方差/漂移。
- **不要把两者混进一个数**——否则就重蹈 `500–1200` 的覆辙。
- 这些都需要先有 **GroundTruth 金标集**作 baseline(同事的标注系统)。在那之前,任务的"可达精度"是未知数,本节是要去测的假设,不是已知结论。

2. 跨条件波动大到多少,就该**转 Pending / 不展示**(而不是硬给一个会漂的数)?
3. 营养结构 P/F/C 要不要也给区间,还是只给点比例?
