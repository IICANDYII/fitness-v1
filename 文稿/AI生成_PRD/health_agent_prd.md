## 0. 本次修订结论

当前健康页面需要明显精简。

健康模块不应完全按照薄荷健康、MyFitnessPal、Keep 饮食记录等传统产品来做。传统饮食 App 的核心逻辑是“用户手动记录食物，系统计算热量和营养素”。Relty 的核心逻辑应该是“硬件和 AI 低打扰观察生活方式，用户确认关键记录，系统生成可信洞察”。

因此，本版本将 Health Agent 从“饮食 AI 记账工具”调整为：

> 面向中高端职场人群的生活方式健康 Agent，通过可控多模态采集，自动识别饮食、室内外、日光暴露和生活节奏，生成克制、可信、可解释的身体状态洞察。

同时，考虑到业务侧仍希望用户看到热量反馈，本版本**保留热量识别与简单摄入展示**。但热量只作为辅助量化指标，展示为估算值或区间，不做首页主视觉，不做“还可吃多少”的账本式体验。

### 0.1 立即砍掉或降级的方向

| 原方向                  | 调整意见            | 原因                        |
| -------------------- | --------------- | ------------------------- |
| 以 kcal 为首页主视觉        | 降级为辅助指标，但保留简单展示 | 可以满足量化反馈需求，但不能变成薄荷健康式热量账本 |
| 碳水 / 蛋白质 / 脂肪作为第一屏核心 | 降级为“粗粒度营养倾向”    | 可展示趋势或占比，不建议精确到克数作为核心     |
| 每日 AI 洞察无条件生成        | 必须基于数据完整度生成     | 无数据时不能说“蛋白质充足”“身体状态良好”    |
| 餐单推荐 / 餐厅推荐          | P2 或暂不做         | 早期分散资源，且不体现硬件差异化          |
| 饮食质量评分               | P1 后置           | 评分会制造伪精确感，前期先做行为洞察        |
| 专业健康报告               | P2 后置           | 与非医疗边界冲突，容易过度承诺           |

### 0.2 本版本保留的核心方向

| 核心方向   | 产品表达                     |
| ------ | ------------------------ |
| 生活方式健康 | 今日生活方式摘要、餐次规律、外食频率、日光暴露  |
| 低打扰记录  | 自动识别 + 用户确认，而不是强迫用户手动记账  |
| 科技感界面  | 少量高密度卡片、状态环、置信度、时间线、轻量趋势 |
| 可信 AI  | 明确数据来源、置信度、数据不足时不输出确定性结论 |
| 长期画像   | 逐步形成饮食习惯、生活节奏、日光暴露和目标偏好  |

### 0.3 热量能力的折中结论

热量识别可以做，但必须换一种产品表达：

| 项目    | 推荐做法                      | 不推荐做法                          |
| ----- | ------------------------- | ------------------------------ |
| 首页展示  | “已确认 2 餐，约 820 kcal，可信度中” | “目标 2180 / 已摄入 823 / 还可吃 1357” |
| 数据精度  | 估算值或区间，如 700-900 kcal     | 精确到个位数                         |
| 统计口径  | 只统计已确认记录                  | 把待确认识别结果自动计入                   |
| 用户心智  | 用于理解趋势和目标匹配               | 用于严格记账和焦虑控制                    |
| AI 建议 | “相对减脂目标，晚餐可更清淡”           | “你今天还能吃 1357 kcal”             |

结论：**热量是辅助指标，不是产品主角。**

## 1. 产品定位

### 1.1 一句话定位

Relty Health Agent 是一个生活方式健康洞察 Agent，不是传统饮食热量记录工具。

它通过可控多模态采集识别用户一天中的饮食、外食、室内外、日光暴露和生活节奏，并将这些行为转化为简洁、可信、可行动的健康洞察。

### 1.2 用户心智

用户不应认为 Relty Health 是：

- 一个需要每天手动输入食物的记账 App
- 一个精准计算每一口热量的减脂工具
- 一个医疗健康诊断产品
- 一个复杂的营养师工作台

用户应该认为 Relty Health 是：

- 一个安静观察自己生活节奏的 AI companion
- 一个帮我发现饮食和生活习惯偏差的身体管理工具
- 一个能给出粗略热量反馈，但不会要求我精确记账的轻量健康工具
- 一个不打扰、不羞辱、不制造焦虑的健康提醒系统
- 一个随着佩戴时间增长越来越懂我的生活方式 Agent

### 1.3 产品边界

| 类型      | 边界说明                             |
| ------- | -------------------------------- |
| 非医疗     | 不做疾病诊断，不输出医疗建议，不替代医生             |
| 非精准热量工具 | 保留 kcal 粗略估算，但不承诺精准，不把热量作为唯一核心指标 |
| 非全天候监控  | 采集状态必须可见，用户可控，默认不展示原始照片 / 视频     |
| 非重度饮食社区 | 不做菜谱社区、打卡社区、餐厅内容平台               |
| 非专业营养师  | 只做生活方式建议，不做复杂营养处方                |

## 2. 目标用户与核心场景

### 2.1 核心用户

| 用户类型        | 特征                | 真正痛点                 | Health Agent 应提供的价值 |
| ----------- | ----------------- | -------------------- | ------------------- |
| 中高端职场人群     | 工作节奏快、外食多、关注状态和形象 | 没时间记录，也不知道生活方式哪里出了问题 | 自动生成生活方式摘要，指出关键偏差   |
| 健身 / 形体管理人群 | 关注减脂、增肌、体态        | 不想长期手动算热量            | 粗粒度判断蛋白质、餐次、训练后补充趋势 |
| 健康入门者       | 有改善意愿但缺乏方法        | 被传统 App 的复杂记录劝退      | 用少量提醒形成习惯           |
| 职业形象管理人群    | 重视体态、精神状态、穿搭呈现    | 饮食、作息、日光暴露影响状态但不可见   | 把身体状态和生活方式联系起来      |

### 2.2 核心使用场景

| 场景    | 用户需求               | Relty 方案                     |
| ----- | ------------------ | ---------------------------- |
| 工作日外食 | 不知道今天吃得是否过重、是否影响状态 | 识别外食场景，提醒高油高盐风险，建议晚餐清淡       |
| 忙碌漏餐  | 忙到忘记早餐或午餐          | 检测餐次缺失，做轻提醒，不制造焦虑            |
| 健身后   | 运动后不知道是否该补充        | 与 Fitness Agent 协同，提示训练后补充建议 |
| 长时间室内 | 一天都在办公室            | 识别日光暴露不足，提示短时户外活动            |
| 减脂期   | 想控制但不想复杂记账         | 提供摄入趋势、外食频率、晚餐时间、蛋白质倾向       |
| 每周复盘  | 想知道本周生活方式变化        | 输出一页式周报，而不是复杂数据仪表盘           |

## 3. 产品原则

### 3.1 克制优先

首页最多展示 3 个核心状态，不堆满营养指标。

推荐第一屏只展示：

1. 今日生活方式状态
2. 今日已识别事件
3. 当前最重要建议

### 3.2 先可信，再智能

AI 不应为了显得聪明而在数据不足时编造结论。

必须遵守：

- 没有饮食记录，不判断营养是否充足
- 只有一餐，不判断全天饮食是否健康
- 识别置信度低，不自动计入正式记录
- 用户未确认的被动识别数据，不写入长期记忆

### 3.3 从“热量账本”转向“生活方式雷达”

首页不再围绕“已摄入 / 还可吃”展开，而围绕：

- 餐次是否规律
- 外食是否偏多
- 日光暴露是否不足
- 饮食是否支持当前目标
- 今日估算摄入是否明显偏高或偏低
- 数据完整度是否足够

### 3.4 科技感不是功能堆叠

科技感来自：

- 清晰状态
- 少量高价值指标
- AI 解释链路
- 置信度和数据来源
- 趋势而非流水账

不是来自：

- 更多图表
- 更多按钮
- 更多营养素
- 更多推荐入口

## 4. 信息架构

### 4.1 App 底部导航

保持当前 5 个入口，但健康模块内部需要重新定义：

| Tab  | 保留 / 调整 | 说明                         |
| ---- | ------- | -------------------------- |
| 今日   | 保留      | 健康首页，展示今日状态和洞察             |
| 记录   | 保留但重构   | 从餐次列表改为“已确认 / 待确认 / 缺失”记录流 |
| 中央 + | 保留      | 快速补录：拍照、语音、文字、手动餐次         |
| 食谱   | 降级或暂隐藏  | 早期不建议作为核心 Tab，容易偏向传统健康 App |
| 我的   | 保留但重构   | 从设置页升级为“健康画像 + 设置”         |

### 4.2 健康首页结构

#### 第一屏：今日状态总览

目标：用户 3 秒内知道今天系统观察到了什么。

展示内容：

| 模块    | 内容             | 示例                    |
| ----- | -------------- | --------------------- |
| 今日状态  | 基于已确认数据生成一句话状态 | “今日数据较少，暂无法判断饮食状态”    |
| 数据完整度 | 高 / 中 / 低      | “低：尚无已确认餐次”           |
| 已识别事件 | 餐次、外食、户外、运动    | “0 餐已确认，1 条待确认”       |
| 今日建议  | 只给 1 条最重要建议    | “先补录最近一餐，AI 才能生成今日洞察” |

#### 第二屏：生活方式雷达

展示 4 个轻量指标：

| 指标   | 表达方式              | 数据来源          |
| ---- | ----------------- | ------------- |
| 餐次规律 | 正常 / 缺失 / 待确认     | 餐次记录 + 时间     |
| 饮食倾向 | 清淡 / 偏重 / 蛋白质可能不足 | 食物识别 + 用户确认   |
| 日光暴露 | 不足 / 适中 / 良好      | 光感 + 室内外识别    |
| 外食频率 | 今日无 / 1 次 / 多次    | 场景识别 + GPS 可选 |

#### 第三屏：AI 洞察

AI 洞察最多 3 张卡片：

1. 当前状态
2. 关键风险
3. 下一步行动

每张卡片必须展示：

- 数据依据
- 置信度
- 是否需要用户确认

## 5. 页面需求

## 5.1 今日页

### 5.1.1 当前问题

当前页面过度强调 kcal、碳水、蛋白质、脂肪，且在无数据时仍展示 AI 判断，容易形成伪洞察。

### 5.1.2 修改目标

把今日页从“热量仪表盘”改为“生活方式状态页”。

### 5.1.3 页面模块

#### 模块 A：顶部问候与状态

文案示例：

> 下午好，KZ\
> 今日数据完整度较低，尚未形成饮食判断

状态可选：

| 状态    | 触发条件            | 文案                   |
| ----- | --------------- | -------------------- |
| 数据不足  | 无确认记录           | “今天还缺少饮食数据，先补录一餐”    |
| 正常观察中 | 有 1-2 条记录       | “已记录部分生活方式，晚些时候生成总结” |
| 可生成洞察 | 有完整餐次或多类数据      | “今日生活方式摘要已生成”        |
| 有偏差   | 出现晚餐过晚、外食多、日光少等 | “今天有 1 个习惯偏差值得关注”    |

#### 模块 B：今日生活方式状态卡

卡片字段：

| 字段   | 示例                |
| ---- | ----------------- |
| 餐次   | “0 餐已确认 / 1 条待确认” |
| 日光   | “尚无有效户外记录”        |
| 外食   | “未识别到外食场景”        |
| 运动关联 | “暂无运动后饮食建议”       |

#### 模块 C：热量与营养趋势卡

热量可以展示，但只做辅助量化反馈，不做第一视觉中心。

| 字段  | 展示方式                                   |
| --- | -------------------------------------- |
| 能量  | “约 820 kcal”或“700-900 kcal”；不展示“还可吃多少” |
| 蛋白质 | 可能不足 / 基本充足 / 数据不足                     |
| 碳水  | 偏低 / 适中 / 偏高 / 数据不足                    |
| 脂肪  | 偏低 / 适中 / 偏高 / 数据不足                    |
| 可信度 | 高 / 中 / 低，必须展示或可点开查看                   |

空状态文案：

> 暂无已确认餐次，无法估算热量和营养趋势。

#### 模块 D：AI 洞察卡

必须遵守数据完整度规则。

无数据时：

> 暂无足够数据生成健康洞察。你可以补录最近一餐，或等待 Relty 自动识别后确认。

有一餐时：

> 已记录午餐。本次餐食可能偏重，晚餐建议选择更轻的蛋白质和蔬菜。该建议基于 1 条餐次记录，置信度中。

有全天记录时：

> 今日餐次较规律，但日光暴露偏少。建议晚饭后进行 10-15 分钟户外步行。

## 5.2 记录页

### 5.2.1 当前问题

当前记录页是传统餐次列表：日期、摄入、目标、还可吃、餐次列表。这种结构没有体现 Agent 的主动识别能力。

### 5.2.2 修改目标

记录页应成为 AI 识别结果的确认中心。

### 5.2.3 页面结构

记录页分为三类：

| 分类   | 说明            | 示例                       |
| ---- | ------------- | ------------------------ |
| 待确认  | AI 检测到但未确认的事件 | “12:36 可能是午餐，包含米饭、鸡肉、蔬菜” |
| 已确认  | 用户确认后的正式记录    | “午餐：鸡肉饭，估算中等热量”          |
| 缺失提醒 | 根据时间和规律推测可能缺失 | “今天尚未记录早餐，是否补录？”         |

### 5.2.4 记录卡字段

| 字段   | 是否必需 | 示例                     |
| ---- | ---- | ---------------------- |
| 时间   | 必需   | 12:36                  |
| 事件类型 | 必需   | 午餐 / 加餐 / 外食 / 户外      |
| 数据来源 | 必需   | Relty 识别 / 手动补录 / 语音记录 |
| 置信度  | 必需   | 高 / 中 / 低              |
| 状态   | 必需   | 待确认 / 已确认 / 已忽略        |
| 快捷操作 | 必需   | 确认 / 修改 / 忽略           |

### 5.2.5 交互要求

用户对待确认记录可以：

- 确认
- 修改食物 / 餐次 / 时间
- 忽略
- 标记“不是食物”

被忽略的数据不进入今日总结，也不进入长期画像。

***

## 5.3 中央 + 快速补录

### 5.3.1 入口目标

中央 + 是健康记录的最低成本入口，而不是复杂表单入口。

### 5.3.2 功能选项

点击 + 后弹出四个方式：

| 方式   | 说明                   | 优先级 |
| ---- | -------------------- | --- |
| 拍照记录 | 拍一张餐食图，AI 识别并生成待确认记录 | P0  |

## 7. 数据与 AI 规则

## 7.1 数据状态定义

| 状态     | 条件                    | 页面表现    | AI 能说什么     | AI 不能说什么        |
| ------ | --------------------- | ------- | ----------- | --------------- |
| 无数据    | 今日无确认记录               | 数据完整度低  | 引导补录、解释无法判断 | “身体状态良好”“蛋白质充足” |
| 单条数据   | 只有一餐或一个事件             | 数据完整度中低 | 评价该事件，不评价全天 | “今日饮食均衡”        |
| 多条数据   | 至少两餐或多类生活事件           | 数据完整度中  | 给出初步趋势      | 医疗判断            |
| 全天较完整  | 早餐 / 午餐 / 晚餐或多个关键事件完整 | 数据完整度高  | 生成今日摘要      | 精确健康预测          |
| 连续 7 天 | 有周期数据                 | 可生成周趋势  | 周规律、偏差、建议   | 诊断疾病            |

## 7.2 AI 洞察生成规则

AI 输出必须符合以下规则：

1. 所有结论必须有数据依据。
2. 数据不足时，明确说“无法判断”。
3. 置信度低时，只输出可能性，不输出确定结论。
4. 建议必须可执行，且一次最多 1-2 条。
5. 不使用羞辱、焦虑、命令式语气。
6. 不输出医疗、疾病、处方级建议。

### 7.3 洞察文案模板

#### 无数据

> 今日暂无已确认饮食记录，暂无法判断营养状态。你可以补录最近一餐，或等待 Relty 自动识别后确认。

#### 单餐

> 已记录午餐，估算约 650 kcal，可信度中。本餐可能偏重，建议晚餐选择更清淡的蛋白质和蔬菜。该判断基于 1 条餐次记录，暂不评价全天饮食。

#### 日光不足

> 今天有效日光暴露偏少。如果时间允许，建议下午或晚饭后进行 10-15 分钟户外步行。

#### 外食偏多

> 本周外食频率较高。若你的目标是减脂，建议优先关注晚餐油盐和主食份量，而不是严格计算每一餐热量。

## 12. 验收标准

### 12.1 P0 验收

| 验收项   | 标准                   |
| ----- | -------------------- |
| 无数据状态 | 首页不输出任何确定性健康判断       |

### 12.2 不合格情况

以下情况视为不合格：

- 今日无记录，但 AI 说“蛋白质摄入充足”
- 低置信度识别结果自动计入今日总结
- 首页第一屏堆满 kcal、碳水、蛋白质、脂肪
- 用户无法知道某条建议来自什么数据
- 身体数据不可用时直接显示“无法加载身体数据”
- 产品文案暗示医疗诊断或精准营养处方

## 14. 最终产品判断

Relty Health Agent 的核心竞争力不是“更准确地算一餐多少卡”，而是：

> 在用户不愿意长期手动记录的前提下，持续、克制、可信地观察生活方式，并把这些行为转化为身体与形象管理建议。

因此，健康页面必须精简。

不是功能越多越专业，而是越少、越准、越可信，越像高端 AI companion。热量可以出现，但只能帮助用户理解趋势，不能重新把产品拉回传统热量账本。

## 15. v2.2 · 跟 demo 对齐的具体落地

本章节是 v2.2 的核心交付，对应 demo 实现，跟开发对接以本章节为准。

### 15.1 信息架构修订（覆盖 §4）

v2.1 §4 给出的「今日 / 记录 / + / 食谱 / 我的」5 Tab + 中央加号已废弃。

**新 4 Tab 框架**（跟 Relty 整体框架统一）：

| Tab | 职责 | Health Agent 在其中的位置 |
|---|---|---|
| **今日** | AI 在替我留意的此刻 | 待确认饮食事件（pending row）+ inline 总览行（已确认 N 餐 · 约 X kcal · 趋势） |
| **沉淀** | 回头看 AI 留意过什么 | 饮食主线（"外食频率在上升"）+ 时间视图里的 meal essence + ask bar 问"我这周饮食怎么样" |
| **画像** | AI 怎么看长期的我 | "生活节奏"维度卡 + 点击进入综合长期详情页 |
| **我** | 设备、隐私、可控感 | 饮食相关偏好（忌口 / 过敏 / 目标）放在此处 |

**严禁**：
- 任何形式的 Health 独立一级 Tab
- 中央加号触发的饮食上传 / 添加流程
- Health 二级页面里再分子 Tab（如"今日 / 记录 / 食谱"）

### 15.2 今日 Tab 中饮食的具体呈现

#### 15.2.1 待确认 row 副信息行（饮食事件专属）

每条饮食事件的待确认 row 必须显示**三行**信息：

```
[essence 缩略图]  事件标题（如"中午的午餐"）           ›
                  时间 · 工作日 · 中等置信
                  约 700–900 kcal · 蛋白质可能偏低
```

第三行规则：
- 必须**区间表达**（如 `约 700–900 kcal`），禁止个位数
- 营养趋势**仅展示一项**（最值得关注的那个 trend），用人话（"蛋白质偏低""碳水偏高"）
- 字号 `11px`，色 `colors.textTertiary`（弱信息）
- 待确认事件**未确认前不计入今日统计**

#### 15.2.2 Inline 总览行（已确认事件汇总）

位置：stats row 下、pending list 上。

```
┌─────────────────────────────────────────────┐
│ 今日饮食 · 已确认 2 餐 · 约 1640 kcal · 蛋白质偏低 →
└─────────────────────────────────────────────┘
```

规则：
- **不是 card**，是上下 hairline 包夹的 1 行字
- 字号 `12px`，hairline `colors.hairline`，色按层级
- 趋势项用 `colors.statusNeedsCare`（暖珊瑚）做轻提示色，**不用红黄绿强评分**
- 数据完整度 < 1 餐时**整行隐藏**（不显示"数据不足"以减少视觉噪声）
- 点击 → 跳「画像 → 生活节奏长期详情页」

### 15.3 沉淀 Tab 中饮食的呈现

**保持现状，不加饮食专属**。

- 主线视图：AI 周期生成的饮食主线（"外食频率在上升""重要会议日通常外食偏轻"）跟其它 agent 主线共池
- 时间视图：饮食 meal essence 跟穿搭 / 运动 essence 按时间共排
- 点击单个 meal essence → 进入「单餐详情页」（见 §15.4）
- ask bar：用户问饮食相关 → 走 Pocket Brain / Chat 通用问答管线（health agent 提供答案上下文）

### 15.4 单餐详情页规范 ⭐

**路由**：`/meal/:id`
**进入路径**：沉淀 Tab → 时间视图 → 点击 meal essence

**必含模块（自上而下）**：

| # | 模块 | 内容 | 视觉规则 |
|---|---|---|---|
| 1 | 顶部 nav | < 返回 + 餐次类型（"午餐 · 外食"）+ ⓘ info | 标准 TopNav |
| 2 | Essence + meta 行 | 左：essence card（80×100）· 右：日期 · 餐次 · `时间段 · 时长` | essence ratio 4/5，dark 中性渐变 |
| 3 | **一句话总结**（衬线 quote） | "以主食为主，蛋白质适中，节奏偏快。" | Fraunces 17px，line-height 1.55 |
| 4 | 粗粒度营养 | 热量区间（约 700-900 kcal）+ 蛋白质/碳水/脂肪 趋势（偏低/适中/偏高，**无克数**） | hairline KV 行，趋势项 statusNeedsCare 标 |
| 5 | 食物分布 | 食物列表 + 占比程度词（"约七成""约一成半""极少"） | **无颜色 bar，无精确百分比**，纯文字 + hairline 分隔 |

### 15.6 「建议改进」carousel 规范

**位置**：单餐详情页末尾 / 生活节奏长期页（可选）

**结构**：4 张可滑动卡片，每张：
- 标题（一句话主题）：如"晚餐从轻""主食减量""换低脂蛋白""补蔬菜"
- 3 个 bullet（具体行动项）：人话化、避免精确克数

**视觉规则**：
- 卡片背景 `colors.bgElevated`，圆角 18px
- 顶部 row：线性灯泡 icon（去色）+ "建议改进" label + `1 / 4` 计数（右对齐）
- bullet 点：直径 4px 圆，色 `colors.textSecondary`，**禁绿色**
- pagination dots：8 个点底部居中，激活态长条 18×5 白色，未激活态 5×5 灰 25%
- bubble-in 动画切换

**文案规则**：
- ❌ 不允许：精确克数（"豆腐 150g""青菜 200g""菌菇 100g"）
- ❌ 不允许：精确百分比（"减少 30%"）
- ❌ 不允许：医疗式命令（"必须""禁止""一定要"）
- ✅ 鼓励：替代品（"豆腐可替代炸物"）
- ✅ 鼓励：程度词（"半碗""一小份""清淡一些"）
- ✅ 鼓励：场景关联（"明日选鱼虾或鸡胸"）

### 15.9 Agent 姿态：反射 + 建议 + 主动场景适配

**反射**：
- AI 主动观察识别，用户轻量确认
- 不打分、不打卡、不催促

**建议**：
- 一日最多 1-2 条主动建议
- 触发场景：单餐结束（详情页 carousel）/ 晚餐前傍晚 hint（今日 Tab 一句话 AI 提示）
- 文案必须基于具体数据（"今天午餐主食偏高，晚餐建议轻一些"），不允许空泛建议

**主动场景适配**：
- 接日历事件（V1.5 上线，V1 用模拟数据）
- 触发场景：
  - 重要会议前一天 → 晚餐建议清淡
  - 出差日历 → 提前提示外食频率上限
  - 长会议日 → 提示午餐时间安排
- 此能力依赖 calendar API 接入，前期可先 mock，UI/PRD 先行

### 15.11 跟 Pocket Brain 的边界

Pocket Brain 是用户**主动捕捉的想法**，Health Agent 是**被动观察 + 用户确认的事件**。两者有重叠场景，规则：

- 用户语音"今天吃了沙拉"+ 在用餐场景（光感 + 时间） → 触发 health pending event（生成待确认餐次）
- 用户语音"我应该多吃蔬菜"（含主张性语气） → 触发 Pocket Brain thought
- 用户语音"沙拉真好吃，想推荐给 Lisa"（关联他人） → Pocket Brain thought
- 边界判断：health agent 处理**摄入事实**，Pocket Brain 处理**主张 / 念头 / 决定**

具体由 LLM 路由判断，需 prompt 工程支持（写入下游 `PROMPT_RULES.md`）。
