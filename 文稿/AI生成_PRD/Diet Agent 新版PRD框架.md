Relty 新版PRD框架

文档目的

本文档用于整合旧版《Relty 指标计算框架》和当前阶段实际推进结果，形成一份可直接用于产品、研发和交接对齐的完整 PRD 框架。

旧版框架形成时间较早，侧重长期方法论、指标边界和跨 Agent 的统一结构；当前版本则已经在 Diet Agent 上形成了更明确的实现方向，包括主界面展示、Balance 计算口径、Goal 命名和 Meal Timing 的产品化理解。因此，本文件的目标不是推翻旧版框架，而是在尽量保留原有结构和逻辑深度的前提下，对当前阶段真正已经变化的部分进行整合。

当前版本统一使用两个核心指标：

Relty Metrics
├── Balance
└── Goal

其中：

Balance = 用户当前状态的客观解释层
Goal = 用户当前目标的推进情况

需要说明的是，旧版框架中的 Finish 在方法论层面仍然有效，但当前整合版文档统一使用 Goal 作为产品层表达。

1. 整体指标体系

1.1 Balance

Balance 是对用户当前状态的客观解释层。

它回答的问题是：

用户当前这类行为本身是否接近相对客观、可解释、可复现的健康或行为标准。

1.2 Goal

Goal 是对用户当前目标推进情况的表达层。

它回答的问题是：

用户今天是否在朝自己当前确认的目标前进。

1.3 Balance 与 Goal 的关系

Balance 与 Goal 必须分开理解。

Balance = 当前状态本身是否健康 / 是否平衡
Goal = 是否推进了当前目标

因此在所有 Agent 中，都可能出现：

Balance 高，Goal 低
Balance 低，Goal 高
Balance 高，Goal 高

2. Diet Agent

Diet Agent 的目标不是单纯识别用户吃了什么，而是将用户每天真实发生的饮食行为转译为少量、可信、可解释的状态信息。

Diet Agent 在当前版本中主要承担三类职责：

1. 识别用户吃了什么、吃了多少、何时吃、是否为本人摄入
2. 计算饮食整体质量与目标推进情况
3. 用尽可能低认知负担的方式把结果展示给用户

因此，Diet Agent 的输出不应只是食物识别结果或营养估算，而应进一步转译为用户能够理解和行动的产品级信息。

2.1 当前核心指标体系

当前版本中，Diet Agent 的核心指标体系不再沿用“Balance + Finish”作为主产品表达，而是统一为：

Diet Metrics
├── Balance
└── Goal

这里需要特别说明：

- 旧版框架中关于 Finish 的方法论、学习期、baseline、gap、目标推荐与追踪逻辑仍然有效
- 但在当前产品表达中，更适合统一使用 Goal 作为面向用户和面向页面结构的名称
- 因此可以理解为：当前版本中的 Goal，继承了旧框架里 Diet Finish 的主要产品功能，但命名上更直接、更容易理解
2.2 Balance

2.2.1 Balance 的定义

Balance 是 Diet Agent 对用户当前饮食状态的客观解释层。

它回答的问题是：

用户今天吃得整体是否健康、是否平衡。

Balance 不代表目标完成度，也不代表是否减肥成功，更不代表用户是否“克制”。

Balance 不应该被理解为：

减肥分数
卡路里打卡分数
目标完成分数
主观满意度分数

当前阶段，Diet Balance 采用组合指标计算，而不是只写成单一 HEI-2020 Total Score。

2.2.2 当前 Diet Balance 公式

当前暂定公式如下：

Diet Balance =
0.40 * HEI_2020_available
+ 0.15 * AMDR_Fit
+ 0.20 * RDA_AI_Adequacy
+ 0.10 * Meal_Timing
+ 0.15 * Kcal_Balance

各模块含义如下：

HEI_2020_available = 整体饮食结构是否接近膳食指南
AMDR_Fit = 碳水、脂肪、蛋白质比例是否合理
RDA_AI_Adequacy = 蛋白质、膳食纤维等关键营养是否达标
Meal_Timing = 用餐时间与个人习惯相比是否稳定
Kcal_Balance = 全天实际热量是否接近个人目标热量 / 能量需求

2.2.3 各模块的产品含义

HEI_2020_available

这是当前 Diet Balance 中最核心的结构质量部分。

它仍然继承旧框架中对饮食质量的基本理解：用户实际吃下去的一组食物，需要被转换为可计算的 food group 和 nutrient components，从而判断其饮食结构是否接近权威膳食指南。

它主要反映的是：

蔬菜、水果、全谷物、乳制品、蛋白质等结构是否合理
精制谷物、添加糖、钠、饱和脂肪等是否需要被控制

AMDR_Fit

AMDR_Fit 用于反映碳水、脂肪、蛋白质的供能比例是否处于合理区间。

它的作用不是替代 HEI，而是补充纯 food-group 结构之外的宏量营养分布信息。

RDA_AI_Adequacy

RDA_AI_Adequacy 用于反映蛋白质、膳食纤维等关键营养是否达到推荐摄入水平。

它更偏向“是否达标”，而不是“是不是越多越好”。

Meal_Timing

Meal Timing 在当前版本中的重点，不是判断绝对意义上的“几点吃饭最健康”，而是判断：

用户当天的用餐时间与其自身习惯相比是否稳定

这里的逻辑是个体内比较，而不是统一的社会时间标准比较。

Kcal_Balance

Kcal_Balance 用于反映全天实际热量是否接近个人目标热量或能量需求。

它不代表减肥是否成功，也不鼓励“吃得越少越好”。它更接近“热量贴合度”，即用户今天是否明显偏离了适合自己的能量区间。

2.2.4 Meal Timing 的当前产品定义

Meal Timing 的当前定义，需要和旧框架做一个明确区分。

旧框架中，Diet Timing 更多被放在独立解释层；而当前版本中，Meal Timing 已进入 Diet Balance 总公式。

但即使如此，Meal Timing 也不应被实现为：

固定时间越早越好
不吃早餐直接扣分
起床后多久必须吃第一餐

当前版本中，更合理的定义是：

Meal Timing = 相对于个人 baseline 的用餐时间稳定性

对于早餐、午餐、晚餐、加餐等餐别判断，当前参考产品侧《场景建模 --产品侧》文件中的定义：

绝对摄入量用于判断 meal / snack
相对用餐时间用于判断 breakfast / lunch / dinner / snack / late_snack
餐别判断依赖用户 baseline_wake_time

因此，Meal Timing 的产品语义不是“最佳时间”，而是“相对于自己是否稳定”。

2.2.5 Balance 的产品解释

Balance 面向用户时，应被解释为“今天整体饮食质量如何”。

它的展示重点应是：

今天整体是否平衡
哪些结构性因素拉高或拉低了结果
是否存在明显风险项

Balance 不应该被解释为：

今天目标完成了多少
今天控制得够不够狠
今天减肥有没有成功

2.3 Goal

2.3.1 Goal 的定义

当前阶段，Diet Agent 的第二核心指标为 Goal。

Goal 回答的问题是：

用户今天是否在朝自己当前确认的饮食目标前进。

Goal 不等于饮食健康质量，也不等于 Diet Balance。

也就是说：

Diet Balance = 饮食健康质量
Goal = 用户当前目标推进情况

2.3.2 Goal 的来源

这一部分原则上仍延续旧框架中的基本方向，即：

Learning Period
→ Baseline Generation
→ Gap Analysis
→ Goal Recommendation
→ User Confirmation
→ Goal Tracking

因此，当前版本虽然在命名上更倾向于使用 Goal，但方法论上仍继承旧框架中的核心逻辑：

- 目标不应完全由用户凭空自由输入
- 系统需要先学习用户真实 baseline
- 系统基于 baseline 和健康参考之间的 gap 给出建议
- 用户确认后，目标才正式成立并进入追踪
2.3.3 Goal 的设置方式

当前阶段，相比先讨论 Goal 展示什么，更需要先明确 Goal 应该如何被创建。

建议当前按以下原则推进：

- 不建议完全由用户自由输入一个精确 Goal
- 更适合由系统提供引导或模板化选择
- 用户在系统推荐基础上进行确认或有限微调
更具体地说，Goal 的产品化形态更适合是：

系统根据学习期发现的问题推荐若干目标模板
→ 用户选择接受、跳过或微调
→ 系统记录为当前 active goal

2.3.4 Goal 的推荐来源

Goal 推荐主要来自以下几类 gap：

1. 饮食结构 gap
2. 热量贴合度 gap
3. 宏量营养比例 gap
4. 用餐时间稳定性 gap

例如：

蔬菜摄入频率不足
水果摄入频率不足
全谷物摄入不足
含糖饮料频率偏高
精制谷物频率偏高
平均能量摄入高于目标区间
用餐时间明显不稳定
late heavy meal 频率偏高

这些 gap 不应全部直接推给用户，而应经过优先级筛选后，只推荐 1–3 个最重要、最确定、最可执行的目标。

2.3.5 Goal 的推荐形式

目标建议更适合以模板化方式出现，而不是抽象营养术语直接裸露给用户。

例如：

每周至少 X 天有蔬菜摄入
每周至少 X 天有水果摄入
每周至少 X 次用全谷物替代精制主食
每周含糖饮料不超过 X 次
每周至少 X 天能量摄入进入目标区间
每周至少 X 天保持相对稳定的用餐时间

2.3.6 Goal 的追踪

Goal 一旦被用户确认，就需要进入持续追踪状态。

当前版本里，虽然不再强调使用 Finish 作为主产品命名，但旧框架中关于目标周期、累计完成、日新增推进的逻辑仍然可保留。

也就是说，Goal 的内部追踪逻辑仍可以保持：

周期累计完成
+ 今日新增推进

但对外展示时，更适合表达为：

当前 Goal 进度
今天是否推进了 Goal

而不是继续面向用户强调 Finish 这一术语。

2.4 Diet Agent 中 Balance 与 Goal 的关系

Balance 和 Goal 必须分开理解，也需要在产品展示上分开表达。

Balance 负责回答：

今天吃得整体是否健康、是否平衡。

Goal 负责回答：

今天是否推进了当前目标。

因此，二者可能出现以下组合：

Balance 高，Goal 低：
今天吃得健康，但没有明显推进当前目标。

Balance 低，Goal 高：
今天推进了目标，但方式不够健康或不够平衡。

Balance 高，Goal 高：
今天既吃得健康，也在推进目标。

这也是当前主界面设计和解释文案需要特别处理的重点。

2.5 Diet Agent 主界面展示方向

当前阶段，Diet Agent 主界面应围绕 Balance 和 Goal 两个核心指标展开。

2.5.1 首屏

首屏需要展示核心指标，同时配合部分分析图表和统计数据，帮助用户快速理解当天的整体饮食情况。

建议首屏优先考虑展示以下内容：

- 今日 Diet Balance 总体状态
- 今日 Goal 完成情况
- 历史趋势入口
- 关键统计数据
- 适量的分析图表
研发推进时，需要同步思考不同数据的呈现形式，例如：

数值卡片
进度条
趋势图
对比条
结构占比图

2.5.2 下滑后可继续展示的信息

除首屏外，其余信息可放置于下滑后的模块中，作为进一步解释与补充：

- 今日最重要的一条饮食反馈
- Balance 分项拆解：饮食结构、热量、宏量营养、关键营养、进食节律
- 每餐记录：早餐、午餐、晚餐、加餐
- 每餐识别出的主要食物
- 每餐热量估算
- 全天总热量估算
- 蛋白质、脂肪、碳水比例
- 蔬菜、水果、全谷物、乳制品、蛋白质等食物组表现
- 高糖、高钠、高饱和脂肪等风险提示
- 饮食记录不完整时的提示
- 识别不确定性 / 置信度提示
2.5.3 页面理解顺序

当前主界面的推荐理解顺序应是：

先看 Balance
再看 Goal
再看图表和统计数据
再看每餐与解释模块

这样能够保证页面首先回答最重要的两个问题：

今天吃得怎么样？
今天有没有朝目标前进？

2.6 Diet Agent 数据与识别要求

Diet Agent 的产品成立前提，不只是公式本身，还依赖较完整的结构化识别能力。

当前至少需要可靠支持以下信息：

食物识别结果
份量估计
热量估计
宏量营养估计
关键营养估计
餐别判断
meal / snack 判断
是否为本人摄入
识别置信度

对于餐别定义，当前以《场景建模 --产品侧》为准：
场景建模 --产品侧
estimated_kcal 与食物构成优先用于判断 meal / snack
相对 baseline_wake_time 的时间位置用于判断 breakfast / lunch / dinner / snack / late_snack
Diet Agent 关注总摄入和营养结构，不要求传统三餐框架本身成立

3. Fitness Agent

3.1 Fitness Agent 的定位

Fitness Agent 对应健身 / 训练相关板块。

它主要处理：

力量训练
器械训练
自重训练
阻力训练
课程训练中具有明确训练目的和训练结构的部分

Fitness Agent 与 Diet Agent 一样，也统一采用：

Balance
Goal

当前阶段，这一板块保留旧版框架中的基本分层思路，但本文件不额外定义新的健身公式，只保留以下对齐结论：

- Fitness Balance 仍然用于表达健身 / 训练状态本身是否接近相对客观标准
- Fitness Goal 用于表达健身 / 训练目标是否被推进
- 旧版框架中关于训练目标追踪的逻辑仍可沿用，但当前整合版统一不再使用 Finish 作为主产品命名
3.2 当前保留的方向

Fitness Agent 当前仍需继续沿用旧版框架中的以下方向：

- 训练行为识别
- 结构化训练记录
- 训练目标推进
- 训练相关趋势和解释层
3.3 当前不新增定义的内容

以下内容本次不做新增定义，仍以后续专项版本为准：

- Fitness Balance 的最终公式
- Fitness Goal 的最终展示形式
- 训练负荷、容量、进阶指标的正式产品口径
4. Activity Agent

4.1 Activity Agent 的定位

Activity Agent 对应日常运动相关板块。

它主要处理：

步行
快走
慢跑
跑步
主动通勤中的步行 / 骑行
其他日常中高强度移动类身体活动

Activity Agent 同样统一采用：

Balance
Goal

当前阶段，这一板块保留旧版框架中的基本思路，但本文件不额外定义新的运动公式，只保留以下对齐结论：

- Activity Balance 用于表达有氧身体活动或日常运动状态本身
- Activity Goal 用于表达运动目标是否被推进
- 旧版框架中关于运动目标追踪的逻辑仍可沿用，但当前整合版统一不再使用 Finish 作为主产品命名
4.2 当前保留的方向

Activity Agent 当前仍需继续沿用旧版框架中的以下方向：

- 日常运动识别
- 活动剂量计算
- 目标推进
- 趋势与解释输出
4.3 当前不新增定义的内容

以下内容本次不做新增定义，仍以后续专项版本为准：

- Activity Balance 的最终公式
- Activity Goal 的最终展示形式
- 步数、MET、活动剂量之间的最终页面表达关系
5. 其他 Agent 板块

当前整合版仍保留旧版框架中的其他板块位置，包括：

Focus Agent
Relax Agent
Rest Agent
Commute Agent

这些板块在整体产品结构上仍然存在，并继续采用：

Balance
Goal

但由于当前阶段没有新的明确口径，本文件不对这些 Agent 做额外定义，只保留其在整体 PRD 中的结构位置，后续仍可基于旧版框架继续展开。

6. 当前仍需继续对齐的事项

当前版本虽然已经形成较明确方向，但仍有若干关键问题需要继续对齐：

- Diet Agent 主界面需要呈现哪些核心信息
- 这些信息之间的优先级如何排序
- “一餐吃完一日全部热量”和“分成多餐摄入”是否存在科学差异，以及该差异是否需要纳入 Balance 或解释层
- Goal 的设置方式最终如何落地
- Goal 的结果在界面上应采用什么表达方式
- 多个 Goal 是否允许并行存在，若允许，页面应如何处理主次关系
- 图表层到底优先服务于 Balance 解释，还是同时服务于 Goal 解释
