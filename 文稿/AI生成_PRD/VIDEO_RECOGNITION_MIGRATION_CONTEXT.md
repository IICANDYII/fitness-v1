# Fitness-v1 视频识别路线讨论迁移说明

> 用途：作为下一轮讨论的上下文。本文只记录已确认的事实、当前判断和建议验证的路线；不把尚未验证的方案写成结论。

## 1. 这轮讨论要解决什么

`fitness-v1` 的视频识别当前卡在 Phase 1：上游把原视频均匀抽成 **1 秒 1 张图片**，再将图片拼成大图交给大模型。实际结果中，拼图常常没有足够的有效动作信息，导致训练/休息切段和后续动作识别不稳定。

导师给出了 `vertical-fitness` 仓库，并建议探索“压缩后直接将视频喂给大模型”的路线。我们阅读后的目的不是简单复用仓库，而是判断其思路对 `fitness-v1` 的启发，以及在当前输入约束下还能怎样提升识别准确率。

## 2. 两个项目分别在做什么

### 2.1 fitness-v1

产品目标是第一人称健身训练识别，并生成训练报告、计划等后续能力。实际识别主链路在 `gym_analyzer/`，而非尚未完成的 agent 编排层。

当前识别链路：

```text
原视频
  -> 上游均匀抽帧：1fps
  -> JPEG 图片 + frames_meta.json
  -> 图片拼图（Phase 1 的主要视觉输入）
  -> 光流摘要 + 可选 IMU 摘要
  -> Gemini Phase 1：切分 EXERCISE / REST / TRANSITION，输出器械时间线
  -> Gemini Phase 2：逐个 EXERCISE 段识别具体动作、组数、次数
  -> 动作映射、报告等下游
```

已知实现特征：

- 抽帧是均匀 1fps，不是语义关键帧抽取。
- 图片被拼成网格供模型整体查看；因此画面会缩小，时间关系也需要模型从空间顺序中自行推断。
- 光流和 IMU 是辅助证据。IMU 已被预处理为运动强度、姿态、峰值、休息等摘要，而非将原始传感器流直接交给模型。
- Phase 2 prompt 已要求输出 `top_candidates`、`rejected_candidates` 等可审计信息，但这些字段尚不等于真正的自动复核流程。

### 2.2 vertical-fitness

它包含两条相对独立的线：

1. 根目录的 fitness assistant：状态评估、恢复建议、训练计划、确认和训练记录。
2. `experiments/fitlab/` 的视频识别实验线：探索把压缩小视频通过 Gemini 原生视频接口直接识别。

其短视频主路径大致为：

```text
原视频
  -> 降帧、缩放、压缩，仍保存为视频
  -> Gemini 原生视频接口
  -> 输出动作时间线、动作名称、次数、器械、场景等
  -> 本地按识别出的训练片段裁剪视频，供复核
```

其长视频处理是固定滑动窗口，不是先智能找动作边界：

```text
0-45 秒
41-86 秒
82-127 秒
...
```

窗口之间默认重叠约 4 秒，目的是避免动作正好被切断。每个窗口独立识别，之后再将同一动作、时间重叠的结果合并；有次数时间点时会去重。

## 3. 两者的关键区别

| 维度 | fitness-v1 当前 | vertical 视频实验线 |
| --- | --- | --- |
| 主要输入 | 1fps 图片拼图 | 压缩后的小视频 | 
| 时间信息 | 被平铺成图片网格 | 以时间序列形式保留 |
| 音频 | Phase 1 拼图路线不包含 | 可随视频保留 |
| 长视频 | 整段图片拼图后做切分 | 固定窗口全覆盖、识别后合并 |
| 主要风险 | 信息过稀、画面缩小、转场帧干扰 | 成本、时延、窗口结果合并、模型对视频接口的实际表现 |

重要澄清：`vertical-fitness` 的优势 **不是** 有一个更聪明的“关键帧抽取算法”。它依旧会降帧，例如 2fps 或 3fps。它的优势在于将画面按时间顺序作为视频输入，并避免把几十张画面进一步缩小到一张静态拼图中。

## 4. 当前新增的硬约束

现阶段无法研究或修改上游抽帧算法。可获得的上游输入只有：

```text
按时间顺序均匀抽取的 1fps 图片
```

因此：

- 无法回到原视频补取关键瞬间；
- 将图片重新合成视频，不会凭空恢复已丢失的帧或精细动作；
- 方案必须围绕“如何更好地组织、筛选和聚合已有稀疏图片证据”。

这意味着问题应定义为：

> 稀疏时序图片识别，而不是完整视频识别。

## 5. 推荐方向：不改上游，也能提升准确率

### 5.1 优先替换“大拼图”输入形式

不要把 60 张图片缩进一张大图后一次判定。将已有 1fps 图片按短时间窗口组织，例如每 10 到 15 秒一组。

```text
已有 1fps 图片
  -> 10-15 秒短序列
  -> 输入模型识别状态、器械、场景
  -> 合并连续训练窗口，形成 EXERCISE 段
```

可比较两种输入：

- B：按时间顺序传入 10-15 张图片；
- C：把同一组图片合成为 1fps 小视频，使用原生视频接口。

两种方式都不会增加原始视觉信息，但都能避免“整段大拼图中单格太小”的二次损失。C 的额外价值是让模型以视频序列形式接收输入；它不是对缺失运动细节的补偿。

### 5.2 先稳定切段，再命名动作

Phase 1 应聚焦更适合 1fps 图片解决的问题：

```text
当前是 EXERCISE / REST / TRANSITION / WALKING？
是否正在使用器械？
是否发生器械或场景切换？
```

它不应过早承担具体动作识别。先得到可靠训练段，再把每段交给 Phase 2 做动作识别，有助于降低上下文混杂和转场干扰。

### 5.3 多帧证据聚合，而非一张拼图一次裁决

对于一个 40 秒训练段，将其拆为多个 10 秒子窗口。每个子窗口独立输出：

- 器械；
- 姿态；
- 运动方向；
- 动作候选及排除理由；
- 证据质量和不确定性。

再结合时间连续性、器械一致性、光流和 IMU 对结果做聚合。目标不是简单多数投票，而是避免一张模糊图、转场图影响整段结论。

### 5.4 候选集 + 对比裁决

不要让模型从全部动作类别直接给唯一答案。建议：

```text
第一步：根据器械、姿态、场景产生 3-5 个候选
第二步：只在候选中做对比，并说明排除依据
第三步：候选接近时触发二次复核；仍不清楚则 UNKNOWN 或仅输出大类
```

特别适用于坐姿划船/坐姿推胸、高位下拉/划船、夹胸/推胸、不同深蹲等混淆家族。

### 5.5 图片质量和证据价值门控

这不是修改抽帧算法，而是对已获得图片进行下游筛选。可为每张图片识别或计算：

- 模糊、遮挡、空镜、转场；
- 器械可见度；
- 手部/身体姿态可见度；
- 是否为训练稳定阶段。

低价值帧不应主导结果；高价值帧应在模型输入和最终解释中获得更高权重。

### 5.6 正确使用光流和 IMU

1 秒间隔的光流不适合精细还原轨迹，也不应单独承担精确计数；但仍可用于：

- 判断是否处于运动或休息；
- 判断粗略方向和周期性；
- 寻找训练中断、休息边界。

IMU 更适合辅助验证运动强度、组间休息、姿态大类以及次数明显偏差。

建议证据职责：

```text
动作名称：器械 + 画面姿态 + 多帧一致性
时间边界：时间连续性 + 光流 + IMU
次数：周期信号 + IMU 交叉验证
```

## 6. 推荐实验顺序

### P0：先建立错误分布

对已有标注样本统计错误属于哪一类：

- Phase 1 训练/休息切段错误；
- 器械识别错误；
- 相似动作混淆；
- 次数错误；
- 转场或低质量帧干扰。

没有这个分布，后续优化容易只改善表面指标。

### P1：输入形式 A/B/C

同一批样本比较：

```text
A：现有 60 张大拼图
B：10-15 秒有序图片序列
C：由同样图片合成的 1fps 短视频
```

指标至少包括：

- 训练/休息切段准确率；
- 器械识别准确率；
- Phase 2 动作 top-1、top-3 准确率；
- UNKNOWN 比例；
- 单条视频成本和耗时。

### P2：短窗口聚合

将表现最好的输入形式接入 Phase 1；以短窗口判定状态与器械，再按连续性合并为训练段。

### P3：只为难例加二次裁决

当候选差距小、处于已知混淆家族、或多窗口结论不一致时，触发对比式复核。普通高确定性样本不增加调用成本。

### P4：产品层的可控不确定性

允许输出 `UNKNOWN_EXERCISE` 或动作大类，并提供候选和证据。在不能可靠识别时不强行给具体动作，可以提升最终结果的可信度；需同时观察覆盖率和准确率的取舍。

## 7. 当前结论

1. “把 1fps 图片拼成视频”可以测试，但不能被视为解决信息缺失的主方案。
2. 在不能改上游抽帧的前提下，最有价值的改造是：**短序列输入 + 多帧证据聚合 + 候选对比复核 + 质量门控**。
3. 首先应替换 Phase 1 的“大拼图”输入和切段方式，尽量复用现有 Phase 2、动作映射、报告等后续资产。
4. 需要先用同一套带标注样本验证 A/B/C，确认哪种输入形式真实提升，而不是只根据模型主观描述下结论。

## 8. 下一轮建议从哪里继续

下一轮可以直接讨论或落地以下任一项：

1. 根据现有 `fitness-v1` 代码，设计 P1 的最小改造方案与接口改动；
2. 明确 A/B/C 实验的样本、标注格式、指标和验收门槛；
3. 设计 Phase 1 短窗口输出 JSON 与时间线合并规则；
4. 设计 Phase 2 的候选对比复核触发条件；
5. 根据历史错误样本建立“混淆动作家族”清单。
