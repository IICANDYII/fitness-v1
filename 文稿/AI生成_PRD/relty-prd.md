# Relty AI Body & Image Pin 产品与 Agent 架构总览

> **版本**：v2.1  
> **状态**：开发指导文档  
> **更新日期**：2026-05-29  
> **适用范围**：Relty 硬件 / Relty App / Fitness Agent / Health Agent / Fashion Agent  
> **核心修订**：从“Agent 功能集合”升级为“AI 穿戴设备的软件-硬件协同架构”

---

## 一、产品定位与愿景

### 1.1 核心定位

> **Relty 是面向中高端职场人群的 AI Body & Image Pin，通过可控多模态采集，识别用户的身体行为、生活方式与职业形象信号，并在 App 中完成确认、解释和长期画像沉淀。**

Relty 的核心不是 App 里的健康、健身、穿搭功能集合，而是一个由硬件持续感知、AI 生成候选事件、用户轻量确认、软件沉淀画像的身体与形象智能系统。

App 不应成为传统健康 App、饮食 App、健身 App 或穿搭 App 的集合，而应作为 Relty 硬件的：

1. **状态面板**：展示设备状态、今日摘要、关键提醒。
2. **确认中心**：承接 AI 识别出的待确认事件。
3. **解释层**：解释 AI 为什么给出某条洞察。
4. **画像层**：沉淀用户的身体、生活方式和职业形象趋势。
5. **权限与信任中心**：管理采集权限、隐私设置和数据保留策略。

### 1.2 统一主线

Relty 产品以 **Body & Image Intelligence** 为统一主线。

| 支柱 | 核心功能 | 产品体现 |
|---|---|---|
| **身体管理** | 运动行为记录、生活方式分析、粗粒度饮食估算 | Fitness Agent + Health Agent |
| **形象管理** | 职业形象分析、穿搭风格反馈、场景匹配 | Fashion Agent |
| **安全陪伴** | SOS 紧急呼叫、位置共享 | 硬件原生功能，P2 |
| **长期画像** | 运动、饮食、日光、穿搭、职业场景趋势 | Body & Image Profile |

### 1.3 产品边界

**Relty 不采集心率、血氧、HRV、睡眠、体温等身体生理数据**，因此不应定义为医疗健康设备，也不应正面竞争 Apple Watch、Oura、WHOOP、Garmin。

Relty 的健康与身体洞察是基于行为、场景、视觉、光感和用户确认数据生成的生活方式建议，不替代医生、营养师、私人教练或医疗级设备。

### 1.4 品牌调性

| 维度 | 要求 |
|---|---|
| 调性 | 高端科技配饰、克制、不炫技、低打扰 |
| 参考 | Aesop、Mejuri、Cuyana、Loro Piana、Arc、Linear |
| 文案关键词 | body & image intelligence, quiet companion, modern professional |
| 不应出现 | 大众减肥 App、绿色健康工具、社区打卡、医生式说教、营养师工作台 |

## 二、总体架构

### 2.1 架构原则

Relty 架构应从“用户主动打开 App 填数据”改为：

```text
设备观察 → 信号处理 → AI 生成候选事件 → 用户确认/修正 → Agent 生成洞察 → 更新统一画像
```

传统 App 链路是：

```text
用户主动输入 → App 计算 → App 展示结果
```

Relty 链路应是：

```text
AI Body & Image Pin 采集生活信号
  ↓
模型识别场景与事件
  ↓
生成待确认事件
  ↓
用户轻量确认、修改或忽略
  ↓
写入正式记录
  ↓
三个 Agent 共同更新 Body & Image Profile
```

### 2.2 软件-硬件协同架构

```text
┌──────────────────────────────────────────────────────────────────────┐
│                         Device Signal Layer                          │
│     摄像头 / 麦克风 / 光感 / 按钮 / 屏幕 / 可选 GPS / 设备状态          │
└───────────────────────────────┬──────────────────────────────────────┘
                                │
                                ▼
┌──────────────────────────────────────────────────────────────────────┐
│                Signal Processing & Event Detection                    │
│      场景识别 / 食物识别 / 运动识别 / 穿搭识别 / 室内外识别              │
└───────────────────────────────┬──────────────────────────────────────┘
                                │
                                ▼
┌──────────────────────────────────────────────────────────────────────┐
│                         Pending Event Layer                           │
│        待确认事件 / 来源 / 置信度 / 状态 / 时间线 / 过期策略             │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ 用户确认 / 修改 / 忽略
                                ▼
┌──────────────────────────────────────────────────────────────────────┐
│                           Agent Layer                                 │
│        Fitness Agent / Health Agent / Fashion Agent                    │
│        运动洞察 / 生活方式健康洞察 / 职业形象洞察                       │
└───────────────────────────────┬──────────────────────────────────────┘
                                │
                                ▼
┌──────────────────────────────────────────────────────────────────────┐
│                    Body & Image Profile Layer                         │
│        身体行为画像 / 饮食与生活方式画像 / 职业形象画像                  │
└───────────────────────────────┬──────────────────────────────────────┘
                                │
                                ▼
┌──────────────────────────────────────────────────────────────────────┐
│                             App Layer                                 │
│        今日摘要 / 事件确认 / 趋势报告 / AI 解释 / 权限设置              │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.3 核心对象：Pending Event

Relty 与传统 App 的核心差异不是“有 AI 分析”，而是 **AI 识别结果不直接变成事实，而是先成为待确认事件**。

#### Pending Event 基础字段

| 字段 | 说明 |
|---|---|
| `event_id` | 事件 ID |
| `event_type` | 事件类型，如 meal、workout、outdoor、outfit |
| `source_type` | 来源，如 device_detected、image_upload、voice_input、manual、system_inferred |
| `confidence` | 置信度，0-1 |
| `status` | detected、pending_confirmation、confirmed、edited、ignored、low_confidence |
| `detected_at` | 检测时间 |
| `confirmed_by_user` | 是否经用户确认 |
| `raw_media_retained` | 是否保留原始图片/视频 |
| `retention_policy` | 数据保留策略 |
| `expires_at` | 待确认事件过期时间 |

#### 状态流转

```text
detected
  ↓
pending_confirmation
  ├── confirmed → 写入正式记录 → 更新画像
  ├── edited → 写入修正后记录 → 更新画像
  ├── ignored → 不计入统计，不写入画像
  └── low_confidence → 仅提示，不生成确定性结论
```

## 三、Agent 体系与职责边界

### 3.1 Agent 职责总览

| Agent | 核心职责 | 能力边界 | 不负责 |
|---|---|---|---|
| **Fitness Agent** | 运动场景识别、运动行为记录、训练片段摘要、运动频次趋势 | 基于视觉/音频/光感识别运动场景，提供行为层反馈 | 精准动作纠正、心率区间分析、医疗级运动建议、代替私人教练 |
| **Health Agent** | 饮食场景识别、室内外识别、日光暴露、生活方式摘要、粗粒度热量估算 | 基于视觉/光感/用户确认数据提供生活方式洞察 | 精准热量计算、医疗诊断、睡眠质量分析、生理指标监测、餐厅推荐、食谱内容流 |
| **Fashion Agent** | 穿搭风格分析、职业形象匹配、正式度判断、颜色倾向分析 | 基于视觉采集分析风格趋势，提供形象管理反馈 | 全身穿搭相册、大众穿搭社区、绝对化审美评判、缺少全身视角时的过度确定结论 |

### 3.2 统一用户画像：Body & Image Profile

三个 Agent 不应各自生成孤立报告，而应共同更新同一个 Body & Image Profile。

| 画像维度 | 数据来源 | 示例洞察 |
|---|---|---|
| 运动连续性 | Fitness Agent | 最近一周运动频次稳定，但强度无法判断 |
| 饮食与生活节奏 | Health Agent | 工作日晚餐偏晚，外食频率较高 |
| 日光与室内外 | Health Agent | 工作日有效日光暴露不足 |
| 职业形象 | Fashion Agent | 近期穿搭以 Business Casual 为主，正式度稳定 |
| 形象管理关联 | Health + Fitness + Fashion | 重要职业场景前，建议减少高盐晚餐并保持轻运动 |

## 四、各 Agent 详细设计

## 4.1 Fitness Agent

### 核心定位

Fitness Agent 不是私人教练，也不是运动手表替代品，而是基于 Relty 可穿戴视觉与环境信号，对用户运动行为进行低打扰记录和趋势总结。

### 核心功能

| 优先级 | 功能模块 | 说明 |
|---|---|---|
| P0 | 运动场景识别 | 通过视觉/音频/光感识别健身房、跑步、瑜伽、骑行等场景 |
| P0 | 运动行为记录 | 记录运动时段、场景标签、来源与置信度 |
| P0 | 今日运动摘要 | 汇总当日运动行为，不涉及心率区间 |
| P1 | 每周运动频次趋势 | 统计本周运动次数及变化趋势 |
| P1 | 训练片段摘要 | 生成短时训练场景摘要 |
| P1 | 运动连续性分析 | 分析运动习惯的连续性 |
| P2 | Apple Health / Google Fit 数据读取 | 仅作为补充数据，不改变非医疗定位 |

### 输入源

| 输入类型 | 内容 | 约束 |
|---|---|---|
| 摄像头 | 运动场景视觉识别 | 按需采集，采集状态可见 |
| 麦克风 | 环境音识别 | 不默认保存原始音频 |
| 光感 | 环境光变化辅助场景判断 | 可低功耗运行 |
| 用户档案 | 运动目标、偏好运动类型 | 用户可编辑 |
| 语音输入 | “开始跑步”“结束训练”等指令 | 用户主动触发 |

### 输出形式

- 今日运动摘要卡片
- 每周运动频次趋势
- 训练片段摘要
- 运动连续性分析
- 可写入统一画像的运动偏好与习惯变化

## 4.2 Health Agent

### 核心定位

Health Agent 是生活方式健康洞察模块，不是传统饮食记账 App，也不是医疗健康 App。

它可以识别饮食场景、粗略估算热量与宏量营养趋势，但热量只是辅助指标，不是产品主心智。

### 关键边界

| 能做 | 不能做 |
|---|---|
| 识别饮食场景和餐次 | 不做精准卡路里账本 |
| 展示粗粒度热量估算 | 不展示“还可吃多少 kcal”作为主视觉 |
| 判断餐次规律、外食频率、日光暴露 | 不做医疗诊断、生理指标监测 |
| 生成生活方式建议 | 不做餐厅推荐、附近商户推荐、外卖推荐 |
| 建议“今晚吃清淡蛋白质和蔬菜” | 不告诉用户“去附近哪家餐厅吃” |

### 热量展示规范

老板需要的“热量识别”可以保留，但必须降级表达。

允许展示：

- “今日已确认 2 餐，估算约 820 kcal”
- “热量估算可信度：中”
- “本餐可能偏高 / 适中 / 偏低”
- “蛋白质可能不足 / 基本充足 / 数据不足”

不建议展示：

- “还可吃 1357 kcal”
- 精确到个位数的热量
- 红黄绿压力评分
- 无确认记录时生成营养结论
- 首页大面积热量仪表盘

### 核心功能

| 优先级 | 功能模块 | 说明 |
|---|---|---|
| P0 | 饮食场景识别 | 通过视觉/音频识别餐次、外食等场景 |
| P0 | 待确认饮食记录 | AI 识别结果先进入待确认状态 |
| P0 | 粗粒度热量估算 | 仅基于已确认记录展示估算值和置信度 |
| P0 | 室内/户外识别 | 通过光感判断室内外状态 |
| P0 | 今日生活方式摘要 | 汇总餐次、外食、日光、数据完整度 |
| P1 | 餐次规律分析 | 分析早餐/午餐/晚餐规律 |
| P1 | 外食频率分析 | 统计外食频次，不进入餐厅推荐 |
| P1 | 日光暴露趋势 | 分析户外时间和日光接触情况 |
| P1 | 每周生活方式报告 | 汇总一周生活方式趋势 |

### 明确不做

| 不做功能 | 原因 |
|---|---|
| 餐厅推荐 / 附近商户推荐 | 属于本地生活服务，会稀释硬件 Agent 的核心价值 |
| 食谱内容流 / 菜谱社区 | 会把产品做成内容 App |
| 主动输入型 UGC | 与 AI 穿戴设备低打扰定位冲突 |
| 复杂餐单推荐 | 早期数据不足，容易变成模板菜谱 |
| 专业健康报告 | 容易越界为医疗或专业营养建议 |

### 输入源

| 输入类型 | 内容 | 约束 |
|---|---|---|
| 摄像头 | 饮食场景识别、环境识别 | 按需采集，默认不长期保存原始影像 |
| 麦克风 | 用餐场景声音识别 | 不默认保存原始音频 |
| 光感 | 判断室内外、日光强度 | 可作为低敏生活方式信号 |
| GPS | 辅助判断通勤、外食场景 | 可选，不用于餐厅推荐 |
| 用户档案 | 饮食偏好、生活习惯目标 | 用户可编辑，可删除 |
| 用户校准 | 确认、修改、忽略识别结果 | 用于提升个性化准确度 |

### 输出形式

- 今日生活方式摘要卡片
- 待确认记录入口
- 粗粒度热量与营养趋势
- 餐次规律分析
- 室内/户外时间趋势
- 日光暴露提醒
- 可写入统一画像的生活习惯变化

## 4.3 Fashion Agent

### 核心定位

Fashion Agent 是职业形象管理 Agent，不是数字衣橱、穿搭社区或大众审美评分工具。

它基于有限视角和用户职业场景，生成克制、可解释、非羞辱性的形象反馈。

### 核心功能

| 优先级 | 功能模块 | 说明 |
|---|---|---|
| P0 | 今日穿搭风格摘要 | 分析当日穿搭风格标签 |
| P0 | 基础颜色/风格标签 | 识别主色调和风格类型 |
| P0 | 基础正式度判断 | 判断穿搭正式程度 |
| P1 | 职业场景匹配度 | 分析穿搭与场景的匹配程度 |
| P1 | 个人风格档案 | 建立用户风格 profile |
| P1 | 每周风格趋势 | 分析一周穿搭风格变化 |
| P1 | 重复风格提醒 | 提醒过于重复的穿搭 |

### 输入源

| 输入类型 | 内容 | 约束 |
|---|---|---|
| 摄像头 | 穿搭视觉采集 | 按需采集，不默认展示原始照片 |
| 用户档案 | 职业、风格偏好、场景需求 | 用户可编辑 |
| 语音输入 | “记录今日穿搭”“分析我的风格” | 用户主动触发 |
| 外部数据 | 天气、日程场景 | 可选，不作为 P0 |

### 输出形式

- 今日形象摘要卡片
- 风格标签
- 正式度评估
- 场景匹配度分析
- 个人风格档案更新
- 可写入统一画像的风格偏好变化

## 五、App 信息架构原则

### 5.1 App 不是功能集合

Relty App 不应把 Fitness、Health、Fashion 做成三个传统垂直 App 的拼盘，而应围绕“设备状态 + 待确认事件 + 今日洞察 + 长期画像”组织信息。

### 5.2 核心页面原则

| 页面 | 定位 | 不应变成 |
|---|---|---|
| 今日页 | 设备状态与今日洞察 | 热量仪表盘、功能入口堆叠 |
| 记录页 | 事件确认中心 | 传统日志账本 |
| 中央 + | 快速校准入口 | UGC 发布入口、复杂表单入口 |
| 健康二级页 | 生活方式趋势与洞察 | 薄荷健康、食谱导航、找餐厅入口 |
| 我的页 | 画像、权限、设备与设置 | 只有设置项的工具页 |

### 5.3 Health 相关导航约束

Health 属于 Relty 的二级能力，不应在 App 中扩展为完整饮食内容产品。

禁止作为核心导航出现：

- 食谱 Tab
- 餐厅推荐
- 附近替代餐厅
- 菜谱社区
- 饮食打卡广场
- 主动 UGC 内容流

允许出现的轻量表达：

- 今日饮食估算
- 待确认饮食事件
- 餐次规律
- 外食频率趋势
- 日光暴露趋势
- 与目标相关的一条轻建议

## 六、共享基础设施

### 6.1 记忆系统：Memory System

所有 Agent 共享统一的用户记忆，确保数据一致性。

| 记忆类型 | 说明 | 存储位置 |
|---|---|---|
| 长期记忆 | 用户档案、职业、风格偏好、运动目标、饮食偏好 | 云端加密存储，用户可删除 |
| 短期记忆 | 当前会话上下文、最近待确认事件 | 设备本地或短期缓存 |
| 事件记忆 | 用户确认的重要生活事件、风格变化、运动习惯 | 云端 + 本地 |
| 画像记忆 | Body & Image Profile 的长期趋势 | 云端加密存储 |

**记忆写入原则**：所有被动采集数据在写入长期记忆前，必须经过用户确认或明确授权。

### 6.2 Pending Event System

Pending Event System 是 Relty 的核心基础设施，负责管理 AI 识别结果从“候选”到“事实”的过程。

必须支持：

1. 事件生成
2. 置信度标注
3. 来源标注
4. 用户确认、修改、忽略
5. 过期清理
6. 是否写入正式记录
7. 是否进入长期画像

### 6.3 调度引擎：Scheduler

负责多 Agent 协同和任务编排。

| 能力 | 说明 |
|---|---|
| 并发控制 | 同一时间最多执行有限数量的图像分析任务 |
| 优先级调度 | SOS 等紧急任务优先于常规分析 |
| 上下文传递 | 跨 Agent 调用时传递用户状态 |
| 低打扰策略 | 避免频繁提醒，优先汇总展示 |
| 设备功耗控制 | 控制摄像头、麦克风等高功耗任务调用 |

### 6.4 硬件接口层

| 硬件模块 | 能力 | 调用约束 |
|---|---|---|
| 摄像头 | 照片采集、短视频采集、场景识别 | 用户授权，采集状态可见；不做默认全天候影像记录 |
| 麦克风 | 语音输入、环境音采集 | 用户授权；不默认保存原始音频 |
| 光感 | 环境光检测、室内外判断 | 可低功耗实时运行 |
| GPS | 通勤、外食场景辅助判断 | 可选；不用于餐厅推荐 |
| 屏幕 | 状态显示、模式切换、采集提示 | 必须显示采集状态和模式状态 |
| 按钮 | 触发采集、快速确认、隐私控制 | 短按/长按区分；作为信任机制入口 |

### 6.5 安全模块

| 安全特性 | 实现方式 |
|---|---|
| 端侧优先 | 敏感数据优先在设备端处理 |
| 加密传输 | 所有云端通信使用 TLS |
| 用户控制 | 用户可查看、编辑、删除数据 |
| 权限管理 | 细粒度权限控制，按需授权 |
| 采集状态可见 | 屏幕或 App 明确显示当前采集状态 |
| 原始影像最小化 | 默认保存结构化结果，不长期保存原始图片/视频 |

## 七、技术栈与开发规范

### 7.1 技术栈统一

| 层级 | 技术选型 | 说明 |
|---|---|---|
| LLM | Groq / OpenAI compatible LLM | 意图路由、prompt 结构化、分析报告生成 |
| 图像识别 | OpenCLIP + FAISS / 多模态模型 | 场景识别、穿搭分析、食物粗识别 |
| 语音处理 | Whisper 或同类 ASR | 语音转文字、环境音事件检测 |
| 数据库 | SQLite 本地 + 云端存储 | 用户数据持久化 |
| 部署形式 | Skill 架构 | 适配硬件 runtime |
| App 原型 | Expo React Native | Web / iOS / Android 原型验证 |

### 7.2 设计原则

1. **硬件优先**：App 是硬件解释层，不是功能堆叠入口。
2. **隐私优先**：被动采集需用户授权，敏感数据端侧优先处理，采集状态明确可见。
3. **待确认优先**：AI 识别结果不能直接当事实，必须经过状态机管理。
4. **低打扰**：避免频繁推送，优先每日/每周摘要。
5. **可解释**：分析结果可回溯到来源、置信度和用户确认状态。
6. **不越界**：不做医疗级健康监测、不做精准动作纠正、不做全天候记录。
7. **克制高级**：少图表、少绿色、少表单、少 UGC，强调状态、趋势和解释。

### 7.3 UI 视觉原则

| 应该 | 不应该 |
|---|---|
| 中性色、低饱和点缀、钛灰、银蓝、冷绿 | 大面积高饱和绿色健康风 |
| 状态胶囊、时间线、置信度标签 | 复杂营养素表格 |
| 设备同步状态、采集状态、待确认事件 | 社区打卡、内容流、餐厅推荐 |
| 克制文案、轻量建议 | 医生式、营养师式、焦虑式话术 |
| 趋势与画像 | 单日流水账和精确数字崇拜 |

### 7.4 交付标准

每个 Agent 需交付：

1. 功能规格文档：明确功能范围、输入输出、边界约束。
2. API 接口定义：与路由层、Pending Event、画像层的交互规范。
3. 数据模型说明：事件、记录、画像、置信度、来源、状态。
4. 测试用例：核心场景、无数据状态、低置信度状态、隐私状态。
5. 性能指标：响应时间、识别准确率、功耗约束。
6. 安全性评估：数据处理流程和权限管理审查。

## 九、能力边界与风险提示

### 9.1 能力边界

| 边界类型 | 说明 |
|---|---|
| 非医疗设备 | 不采集生理数据，所有健康建议仅供参考，不替代专业医疗诊断 |
| 非专业教练 | 不提供精准动作纠正，仅做运动行为记录和趋势分析 |
| 非精准营养工具 | 饮食识别仅做粗粒度趋势和估算，不保证精确热量计算 |
| 非本地生活服务 | 不做餐厅推荐、附近商户推荐、外卖推荐 |
| 非 UGC 内容平台 | 不做食谱社区、打卡社区、穿搭社区 |
| 非穿搭相册 | App 不展示原始照片/视频，重点是风格分析和趋势 |
| 隐私保护 | 默认不记录对话，默认不长期保存原始影像，用户可控可删 |

### 9.2 风险清单

| 风险 | 严重度 | 应对措施 |
|---|---|---|
| 隐私与社交接受度 | 高 | 采集状态明确可见、用户可控传感器开关、默认不展示原始数据 |
| 软件功能膨胀，变成健康/穿搭/饮食 App 集合 | 高 | 明确 App 是硬件解释层；删除餐厅、食谱社区、UGC、复杂餐单等非核心功能 |
| 场景识别不准确 | 中 | 多模态数据交叉验证、用户确认闭环、持续模型优化 |
| AI 无数据时胡说 | 高 | 所有洞察必须读取数据完整度和置信度，低数据不输出确定结论 |
| 功能低频使用 | 高 | 设计每日/每周摘要作为打开理由，强化身体与形象管理统一叙事 |
| 与智能手表竞争 | 中 | 明确差异化定位，聚焦身体与形象管理，不做生理监测 |
| 硬件佩戴体验 | 中 | 强化高端配饰设计、优化佩戴结构、控制重量体积 |
| 大众健康 App 视觉化 | 中 | 采用克制科技感设计，不使用大面积绿色、营养仪表盘、打卡风格 |

## 十二、最终判断

Relty 的核心竞争力不是 App 里有多少健康、饮食、健身、穿搭功能，而是：

> **用一个高端、克制、可信的 AI 穿戴设备，持续观察用户的身体行为、生活方式与职业形象，并通过少量确认和可解释洞察，沉淀长期 Body & Image Intelligence。**

因此，所有产品和开发决策都应遵守：

1. 硬件信号优先，不做纯 App 功能膨胀。
2. 待确认事件优先，不把 AI 识别直接当事实。
3. 生活方式洞察优先，不做医疗、精准热量和本地生活推荐。
4. 克制高级优先，不做大众健康 App、UGC 社区和复杂内容导航。
5. 统一画像优先，不让 Fitness、Health、Fashion 变成孤立功能。
