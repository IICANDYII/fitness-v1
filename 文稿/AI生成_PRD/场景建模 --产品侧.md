# 场景建模 \-\-产品侧

# **Diet 场景建模 v0：识别准确度优先的维度收敛说明**

## **核心原则**

绝对摄入量用于判断一次摄入是 **正餐 meal** 还是 **加餐 snack**；相对用餐时间用于判断该次摄入属于 **早餐 / 午餐 / 晚餐 / 夜宵**。

Diet Agent 本身关注的是用户的 **总摄入情况** 和 **营养结构**，因此不判断用户的用餐形式是否符合传统三餐。但系统需要记录每一次用餐，并为每一次摄入 episode 输出餐别。

Diet 场景建模不追求完整理解用户所处场景，只保留能提升以下四类准确度的信息：

- **Food Identity Accuracy**：用户点了什么 / 吃了什么 / 喝了什么。

- **Inventory Completeness**：这次摄入包含哪些 item，是否漏识别。

- **Portion Accuracy**：用户实际摄入了多少。

- **Ownership Accuracy**：哪些食物 / 饮品属于用户本人。

---

## **正餐 vs 加餐定义**

Diet Agent 按摄入绝对值区分正餐和加餐：

```Plain Text
meal = 摄入规模达到正餐阈值
snack = 摄入规模低于正餐阈值
```

v0 可先使用 estimated\_kcal 作为主判断依据：

```Plain Text
estimated_kcal >= 350 kcal → meal
estimated_kcal < 350 kcal → snack
```

如果热量估计不稳定，可用食物构成辅助判断。

更倾向 meal 的情况包括：包含明显主食 \+ 蛋白质来源，包含完整餐盘 / bowl / 便当 / 套餐，多个 item 共同构成一次主要摄入，或饮品 \+ 主食 / 三明治 / 沙拉 / 饭面类组合。

更倾向 snack 的情况包括：只有饮品，只有水果 / 坚果 / 饼干 / 小甜点 / 小包装零食，或单个小食份量明显不足以构成正餐。

判断优先级建议为：

```Plain Text
estimated_kcal > food composition > container / package size > scene prior
```

场景只能作为弱辅助，不能主导 meal/snack 判断。

---

## **餐别定义**

Diet Agent 不按社会标准时间判断早餐、午餐、晚餐，而是按用户个人作息判断。

```Plain Text
餐别 = 摄入发生时间相对于用户 baseline_wake_time 的位置
```

其中：

```Plain Text
baseline_wake_time = 用户近期稳定起床时间
baseline_sleep_time = 用户近期稳定入睡时间
```

baseline 可由用户历史行为、睡眠记录或系统推断获得。

每次 episode 只输出一个字段：

```Plain Text
meal_label
```

可选值：

```Plain Text
breakfast
lunch
dinner
snack
late_snack
```

判断顺序：

```Plain Text
Step 1：根据绝对摄入量判断 meal / snack
Step 2：如果是 snack，根据相对时间输出 snack 或 late_snack
Step 3：如果是 meal，根据相对时间输出 breakfast / lunch / dinner
```

v0 相对时间区间：

```Plain Text
0–3h after wake     → breakfast
3–8h after wake     → lunch
8–14h after wake    → dinner
14h+ after wake     → late_snack
```

如果该 episode 已经被判定为 snack：

```Plain Text
0–14h after wake    → snack
14h+ after wake     → late_snack
```

---

## **场景重叠原则**

场景可以重叠，例如 meeting \+ eating、commuting \+ drinking、working \+ eating。

Diet Agent 的触发条件不是“当前主场景是不是用餐”，而是：

```Plain Text
是否存在实际食物 / 饮品摄入
```

只要存在实际摄入，就需要创建 `diet_episode`。

“茶歇”不作为 Diet Agent 的独立分类词条。原本可能被叫作“茶歇”的摄入，在 Diet Agent 中统一根据摄入绝对值归为 `snack`；如果摄入量达到正餐阈值，则归为 `meal`。

## **Diet v0 需要关注的场景信息**

以下信息不存在严格先后顺序。它们的共同标准是：是否能真实提升食物识别、份量估计、摄入归属判断的准确度。

### **4\.1 店铺招牌 / 品牌 logo / 店名**

店铺招牌需要保留，但它的价值取决于店铺类型。

如果识别到的是连锁餐厅或标准化品牌，店名 / logo 可以直接连接标准菜单、标准份量、SKU 或 nutrition database，因此能精准协助识别和计算。

如果识别到的是非连锁独立餐厅，店名本身对当次食物识别和营养计算的帮助有限。它更多只能用于理解用户长期用餐习惯，或在能进一步匹配到菜单 / 历史记录 / 可检索信息时作为辅助 evidence。因此，非连锁店名不应被视为强识别依据。

---

### **4\.2 菜单 / 点单屏 / 价目表**

菜单识别的核心价值是获取具体菜名、SKU、规格和加料选项，而不是泛泛判断“这里是餐厅”。

这类信息对 Food Identity Accuracy 价值很高，尤其适用于视觉上难以直接判断的饮品、套餐、混合碗、外卖和标准化菜品。

---

### **4\.3 点餐语音 \+ 说话人归属**

“谁在说话”需要保留，但保留原因不是社交分析，而是点餐信息归属。

Diet Agent 需要尽可能识别用户本人点了什么，并区分用户、店员和同行者，避免把他人的订单记入用户摄入。

建议字段：

```Plain Text
ordering_speaker_attribution
```

---

### **4\.4 包装文字 / 杯身贴标 / 外卖标签 / 小票**

这类信息可以提供具体菜名、SKU、规格、加料和品牌信息。

对于外卖、奶茶、咖啡、包装食品，这类文字信息往往比视觉食物图像更可靠。

---

### **4\.5 餐前全貌 / 餐后剩余 / 餐前后差值**

餐前全貌用于判断这次摄入包含哪些 item 以及初始份量。

餐后剩余用于判断用户实际吃掉了多少。

餐前后差值是 episode 建模相对于单帧识别的核心增益机制：

```Plain Text
actual_intake ≈ before_meal_amount - after_meal_remaining
```

---

### **4\.6 焦点食物 / 饮品有无、大类、数量与布局**

需要识别本次 episode 是否存在食物 / 饮品，以及焦点物的大类、数量和布局。

这类信息用于建立 food / drink inventory，判断是否存在漏识别，也帮助区分单人餐、多 item 组合、套餐和共享场景。

---

### **4\.7 容器类型与容器容量**

容器类型和容量可以为 portion estimation 提供先验，例如 cup、bowl、plate、bento\_box、takeout\_box、package、sauce\_container 等。

容器容量只有在识别置信度较高时使用。如果容器大小无法可靠估计，不应硬算。

---

### **4\.8 独享 vs 共享、同伴人数、同伴 vs 路人**

这类信息只用于 Ownership Accuracy。

Diet Agent 不关心社交关系本身，只关心这些信息是否影响摄入归属和份量拆分。

需要避免把整桌共享菜全部计入用户，也需要避免把路过的人误判为共餐者。

---

### **4\.9 Episode 相位与转场**

需要识别 episode 相位和边界，用于判断什么时候抓菜单、什么时候抓餐前全貌、什么时候抓餐后剩余。

建议相位：

```Plain Text
approach
enter
ordering
served
before_intake
intaking
after_intake
exit
```

转场 / 起始 / 离开用于定义当前 diet episode 的边界。

---

### **4\.10 画质 / 遮挡 / 分辨率 / 传感可用性**

这类信息作为横切置信层，用于决定识别结果是否可信、是否需要弃权、是否需要触发高分辨率抓拍。

---

## **可作为弱辅助的信息**

以下信息可以辅助判断，但不能作为强识别依据：

- GPS / 地理围栏：可辅助锁定场所身份，但不能作为单点强 evidence。

- 餐饮场所品类：可粗略约束候选空间，例如 restaurant、cafe、fast\_food、cafeteria、home、office\_delivery、street\_food。

- 餐具类型：可作为弱菜系 / 食物形态 prior，例如 chopsticks、fork、spoon、handheld、straw。

- 用户在空间中的位置：可辅助判断 episode 相位，例如 counter、queue、seat、table、entrance、exit。

- 用餐时间：只用于结合 baseline wake\_time 输出 meal\_label，不按社会标准时间解释。

---

## **不进入 Diet v0 主链路的信息**

以下信息不直接服务于 Diet 识别准确度，原则上不进入 v0：

```Plain Text
工作日 vs 周末
茶歇，作为独立词条删除
社交属性：工作餐 / 朋友聚餐 / 商务餐
餐厅档次 / 装潢风格
新颖 vs 例行，作为独立字段删除
体姿
运动强度 / 节奏
天气
人流密度
普通环境声 / 音量 / 音乐
穿着
社交正式度
关系类型
幻灯 / 白板 / 文档
器械标签
衣物吊牌
```

补充说明：

```Plain Text
谁在说话不删除，但只保留在点餐语音归属里，不作为社交理解维度。
环境声只有在影响点餐语音质量时才有价值，否则不进入主链路。
```
