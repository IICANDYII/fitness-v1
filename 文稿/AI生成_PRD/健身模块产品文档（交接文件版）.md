# 健身模块产品文档

## 1\. 模块背景

该模块基于胸前第一人称设备，通过图片序列 / 视频素材 /  IMU 数据，识别用户是否在健身、做了什么动作、练到了哪些肌群，并在训练前生成计划、训练后生成总结报告。

当前健身模块的核心目标不是直接做成专业教练替代品，而是围绕“记录设备”的定位，帮助用户低成本记录训练过程，并基于训练数据生成可理解、可反馈、可持续优化的健身报告。

## 2\. 当前整体进展

### 2\.1 已跑通的部分

1. **训练素材 → 训练总结生成**

- 已经可以基于员工录制的视频 / 图片素材生成训练总结。

- 总结方向包括：训练内容、肌群覆盖、完成情况、表现反馈、恢复建议等。

2. **员工数据采集流程初步建立**

- 目前员工录制方式是整段健身过程视频，从进入健身房到训练结束。

- 已讨论过视频文件过大、NAS上传慢等问题，目前依靠飞书进行视频压缩后上传数据至NAS中。

3. **动作库与训练计划库初步整理**

- 已筛选出适合第一人称设备识别的健身房常见动作。

- 已关注胸、背、肩、腿、臀、核心、有氧等主要训练类别。

- 后续应当对动作数据库通过实际录制数据再一次进行筛选以及修改。

4. **模型评估方向已明确**

- 当前模型已确定使用 Gemini 3 Flash。

- 优化重点不再是更换模型，而是通过提示词、输入结构和数据组织方式提升输出稳定性。

- 建议用时间轴对齐方式评估模型输出，指标包括动作识别准确率、训练阶段识别、时间段 IoU、边界误差、组数 / 次数估计误差等。

## 3\. 当前产品判断

### 3\.1 健身模块定位

当前产品是一个第一人称记录设备，不是传统专业健身 App。因此健身模块首页更适合优先呈现“昨日 / 上一次训练报告”，而不是一打开就让用户制定计划。

推荐结构：

1. 首页：上一次训练总结

2. 训练记录：训练时间线、动作、肌群、完成情况

3. 计划：根据用户目标和可用器械生成下一次训练建议

4. 对话：用户可以追问训练表现、调整计划、解释报告

### 3\.2 MVP 阶段建议

MVP 不建议一开始追求完全自动识别准确，而是采用：

- 模型自动生成训练 timeline 草稿

- 用户进行轻反馈确认

- 系统基于用户反馈修正训练记录

- 这些确认数据反哺模型和提示词优化

这样做的价值是：即使模型还不够精准，也可以先跑通真实产品闭环，同时收集真实用户数据。

### 3\.3 当前优先级

建议识别优先级为：

1. 用户是否在健身

2. 当前是有氧还是无氧

3. 当前使用什么器械 / 场景

4. 当前做的动作是什么

5. 练到什么肌群

6. 做了几组、每组几次

不建议一开始把“组数和次数”作为最高优先级，因为单靠第一人称图片序列很难稳定判断，需要结合 IMU、节奏特征或用户轻反馈。

## 4\.Fitness Balance 指标说明

Fitness Balance 是健身模块中用于衡量用户近期训练是否均衡的核心指标。它不是单纯判断“用户有没有运动”，而是判断用户在最近一段时间内是否训练到了主要肌群，以及训练刺激是否过度集中在少数部位。

该指标更适合放在训练报告和周分析中，用来回答用户：

- 这周训练是否均衡？

- 哪些肌群练得比较充分？

- 哪些肌群被忽略了？

- 是否连续多次集中训练同一批肌群？

- 下一次训练是否需要补充某些部位？

---

### 4\.1 指标定位

Fitness Balance 的产品定位是“训练均衡度提示”，不是专业训练计划判定。

它主要服务于三个场景：

1. **训练后报告**

    - 告诉用户本次训练主要覆盖了哪些肌群。

    - 提示本次训练是否过于集中在某些部位。

2. **每周分析**

    - 展示最近 7 天主要肌群覆盖情况。

    - 告诉用户哪些肌群训练不足。

3. **下一次训练建议**

    - 根据近期肌群覆盖情况，提示下次可以优先补充的部位。

    - 例如：本周胸、背训练较多，但腿部和核心覆盖较少，下次可优先安排腿部或核心训练。

---

### 4\.2 当前指标设计思路

Fitness Balance 不建议只用“是否练到某个肌群”来计算，因为这样会出现一个问题：

如果用户最近 7 天训练了 4 次，但每次都只练臂、腿、背，那么从第二次训练开始，分数可能停在某个固定值不变，无法反映“重复训练同一批肌群”的问题。

因此当前建议的计算逻辑应同时考虑：

1. **肌群覆盖**

    - 最近 7 天是否覆盖到主要肌群。

2. **训练分布均衡**

    - 训练是否过度集中在少数肌群。

3. **重复集中风险**

    - 是否连续多次训练同一批肌群，而忽略其他肌群。

4. **用户不想明显增肌的部位**

    - 目前用户目标不做复杂分类，只保留一个简单问题：

    - “有没有不想明显增肌的部位？”

    - 如果用户选择某些部位不想明显增肌，则这些肌群在 Balance 计算中的权重降低，避免系统过度鼓励用户补练这些部位。

### 4\.5 当前未完成事项

接手人后续需要继续推进：

1. 确认最终肌群分类；

2. 完善动作 → 肌群权重表；

---

### 4\.6 交接建议

Fitness Balance 后续不要只交给研发按公式实现，产品侧需要持续校验：

1. 分数是否符合用户直觉；

2. 分数变化是否能解释；

3. 用户是否知道自己为什么被扣分；

4. 下一次训练建议是否和分数原因一致；

5. 不同训练目标下是否需要调整肌群权重。

这个指标的关键不是追求教练级精度，而是让用户能理解分数原因，让研发能稳定实现，同时保证结果不违背基础训练逻辑。

## 5\. 当前关键问题

### 5\.1 数据量不足

目前主要数据来自内部员工录制，数量不够，导致模型优化和动作覆盖都受限制。

建议后续继续推进：

- 每个核心动作至少采集 5–10 条不同员工素材

- 每条素材尽量包含完整的一组或多组动作

- 优先覆盖高频动作，而不是追求动作库数量

- 每条素材必须绑定训练计划 ID 和动作清单

### 5\.2 标注成本高

完整人工打标成本较高，不建议所有数据都做精细标注。

建议分三层标注：

1. 轻标注：是否在健身、动作大类、开始结束时间

2. 中标注：具体动作、器械、训练阶段、是否完成

3. 精标注：组数、次数、每组起止时间、动作质量

前期重点做轻标注和中标注，精标注只用于模型评测样本。

### 5\.3 第一人称视角识别存在天然限制

部分动作在第一人称视角下容易混淆，例如：

- 绳索下压 vs 面拉

- 绳索弯举 vs 绳索下压

- 固定器械推胸 vs 固定器械推肩

- 部分背部动作和肩部动作

- 被器械遮挡的动作

建议不要只依赖单帧图片，而是结合：

- 前后动作序列

- 器械识别

- 身体运动方向

- IMU 加速度 / 角速度节奏

- 训练计划中的动作候补

- 用户所在健身房器械信息

## 6\. IMU 数据方向

最近开始尝试使用 IMU 数据辅助动作识别和组数 / 次数判断。

### 6\.1 当前判断

IMU 数据中最有价值的是：

1. **加速度**

- 用于判断运动节奏、动作周期、次数。

2. **角速度**

- 用于判断身体或设备旋转变化，对动作类型有帮助。

3. **角度**

- 可作为姿态变化参考，但受佩戴位置影响较大，单独使用不稳定。

### 6\.2 IMU 可做的事情

IMU 不建议直接交给大模型处理原始数据，而是先通过脚本提取结构化特征，再给大模型或规则系统使用。

建议提取的特征包括：

- 活动段开始 / 结束时间

- 动作周期数量

- 主运动轴

- 加速度峰值

- 角速度峰值

- 周期稳定性

- 是否存在明显组间休息

- 动作大类候补

### 6\.3 IMU 对产品的价值

IMU 更适合辅助判断：

- 当前是否在运动

- 一组动作什么时候开始 / 结束

- 大概做了几次

- 动作节奏是否稳定

- 是否存在组间休息

IMU 不适合单独判断具体动作名称，最好与图片序列、训练计划和器械识别结合。

## 7\. 后续建议工作

### 7\.1 短期

1. 完成员工素材管理表搭建

2. 明确核心动作采集清单

3. 每个核心动作采集多名员工素材

4. 结合 IMU 提升组数 / 次数识别稳定性

5. 固定模型输入格式，例如：

- 用户训练计划

- 图片序列

- IMU 特征摘要

- 已知动作候补

6. 建立每日提示词优化评测表

7. 输出模型识别结果与人工标准答案对比

### 7\.2 中期

1. 完成 MVP 用户轻反馈流程

2. 完成Balance指标定义

3. 跑通“模型输出 → 用户确认 → 数据回流”的闭环

### 7\.3 长期

1. 将用户历史训练数据用于个性化计划调整

2. 结合健身房器械识别做场地记忆

4. 构建更细的训练负荷、肌群覆盖、恢复建议体系

5. 从“训练记录”逐步过渡到“训练建议”和“长期趋势分析”

## 8\. 建议接手人优先关注

接手后建议先不要急着扩展复杂功能，而是先确认以下四件事：

1. 当前数据是否能稳定管理

2. 当前核心动作是否有足够样本

3. 当前模型输出是否有统一评测标准

4. 当前训练报告是否能形成稳定产品体验

如果这四件事没有稳定，后续继续扩展动作库、计划库或复杂 Agent 能力，都会导致产品判断变得更混乱。

## 10\. 风险与注意事项

1. 不要过早承诺自动识别组数和次数非常准确，目前数据和传感器条件还不够稳定。

2. 不要把健身模块包装成专业教练替代品，当前更适合作为训练记录和总结工具。

3. 不要只看模型单次输出效果，要建立可量化评测。

4. 不要盲目扩充动作库，优先覆盖高频、第一人称可识别、员工容易录制的动作。

5. 不要忽视素材管理，数据命名和计划绑定会直接影响后续模型优化。

6. 不要让用户承担过重纠错成本，MVP 阶段应采用轻反馈，而不是要求用户完整标注训练过程。

## 11\. 我个人的建议

健身模块下一阶段最重要的不是继续增加功能，而是把“数据—识别—反馈—优化”这个闭环跑稳。

推荐优先路线：

员工素材规范采集
→ 模型生成训练 timeline
→ 人工 / 用户轻反馈修正
→ 形成标准答案
→ 每日量化评估提示词优化效果
→ 输出更稳定的训练报告
→ 再逐步加入 IMU、健身房器械记忆等能力

这样可以让研发、产品和数据采集团队都知道每天在优化什么，也能让管理层看到准确率和体验在持续提升。
